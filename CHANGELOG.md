### 🐛 Fixed

- **iOS — un flip de caméra pendant une bascule audio/vidéo (ou un hold, un restart ICE, une renégociation entrante) pouvait laisser la caméra physiquement allumée et en train de streamer alors que l'app affichait la vidéo comme désactivée** : `CallManager.switchCamera()`/`selectCamera(id:)` déclenchent chacun leur propre cycle `stopCapture()`→`startCapture()` sur le `RTCCameraVideoCapturer` partagé (`WebRTCService.switchCamera(completion:)`/`switchToCamera(uniqueID:)`), mais n'étaient jamais sérialisés contre la famille `videoToggleTask`/`holdVideoTask`/`survivalVideoTask`/`iceRestartTask`/`signalOfferAnswerTask` qui pilote `upgradeToVideo()`/`downgradeFromVideo()` sur le même capturer — ces deux méthodes ne vérifient jamais `Task.isCancelled` en cours de vol (elles attendent `stopCapture`/`startCapture`), donc un flip caméra déclenché juste après un tap « désactiver la vidéo » pouvait laisser le `startCapture()` du flip se terminer APRÈS le `stopCapture()` du downgrade concurrent — régression de confidentialité (LED caméra allumée, flux actif) plutôt qu'un simple désync d'UI. Audit initial en Vague 64 (spec prête, non exécutée faute d'accès compilateur) ; un 10ᵉ site concerné (le downgrade vidéo du handler thermal-critique) manquait de l'énumération initiale, découvert par re-grep exhaustif avant implémentation. Correctif : nouvelle propriété `cameraSwitchTask`, chaînée (pas annulée) dans les deux sens — `switchCamera()`/`selectCamera(id:)` attendent désormais les 5 autres tâches avant d'actuer (pont `withCheckedContinuation` pour que l'attente couvre la fin réelle du switch, pas son enqueue), et chacun des 10 sites existants attend désormais `cameraSwitchTask` avant sa propre actuation. `WebRTCService.switchToCamera(uniqueID:)` gagne un paramètre `completion` optionnel (défaut `nil`, rétrocompatible) miroir de `switchCamera(completion:)`. Vérification par tests source-guard (`CallManagerCameraSwitchSerializationTests`, 17 tests) — pas de toolchain Swift dans ce sandbox, verdict de compile laissé à la CI macOS.

- **Gateway — après une remise à zéro des préférences d'une conversation, TOUT changement suivant (épingler, mettre en sourdine, archiver) était silencieusement jeté par les autres appareils** : `UserConversationPreferences.version` est déclaré **monotone** par le schema lui-même (« Monotonic version for optimistic-concurrency resolution […] clients drop incoming payloads whose `version` is <= their local snapshot ») et le SDK iOS applique littéralement cette règle (`ConversationStore.applyRemote` : `event.version <= conv.userState.version → return`, le reset conservant la version reçue). Or le compteur vit **sur la ligne** : `DELETE /user-preferences/conversations/:id` diffusait un reset porteur de `version = ligne.version + 1` puis **supprimait la ligne**, si bien que le `PUT` suivant retombait dans la branche `create` de son `upsert` et repartait à `version: 1` — en dessous du reset que les autres appareils venaient d'enregistrer. Un utilisateur ayant remis ses préférences à zéro depuis un appareil voyait donc son épinglage suivant appliqué **localement seulement** ; les autres sessions le jetaient, ainsi que chacun des changements ultérieurs (chaque `version` restant sous le plancher du reset), jusqu'à un refetch complet fortuit — divergence **permanente**, pas différée. Le commentaire de la branche `create` montre l'angle mort : il justifie `version: 1` pour que le reset (create → delete) ne soit jamais pris pour un no-op, sans considérer la transition inverse (delete → create) — les deux sens d'une même paire, un seul audité. Correctif : le reset restaure les colonnes de préférence à leurs valeurs par défaut **en place** en incrémentant `version` dans la même écriture atomique (`update`), de sorte que la séquence traverse le reset ; `version` est un état de protocole, pas une préférence utilisateur, et une remise à zéro ne doit pas le rembobiner. L'écriture unique supprime au passage la course lecture-puis-écriture de l'ancien `findUnique` + `delete`. Contrat REST inchangé (ligne absente → P2025 → 404). `CONVERSATION_PREFERENCES_DEFAULTS` gagne `mentionsOnly` et `clearHistoryBefore`, absents de l'instantané par défaut alors qu'ils font partie du payload diffusé (`ConversationPreferencesPayload`) — sans quoi un reset laissait `mentionsOnly: true` en base pendant que les clients appliquaient `false`. Régressions couvertes (RED→GREEN) dans `services/gateway/src/__tests__/conversation-preferences-broadcast.test.ts` par une séquence réelle épingle → sourdine → reset → ré-épingle pilotée par un double de store **vivant** : les mocks figés existants rejouaient la version codée en dur par le test, donc aucune assertion ne pouvait voir la séquence redescendre (RED observé : `1` émis après un reset à `3`).

- **Gateway — une édition ou une suppression de message faite en REST n'atteignait JAMAIS les participants hors ligne (le chemin PRIMAIRE d'iOS)** : le transport socket (`MessageHandler.handleMessageEdit` / `handleMessageDelete`) enfile la mutation dans la file de livraison pour chaque participant hors ligne, précisément parce que — selon son propre commentaire — « without this, an edit or delete made while a recipient is offline is lost for them ». Les **cinq** routes REST qui mutent le même message (`routes/messages.ts` PUT + DELETE `/messages/:messageId`, `routes/conversations/messages-advanced.ts` PUT `/conversations/:id/messages/:messageId`, DELETE idem, PATCH `/messages/:messageId`) diffusaient bien `message:edited` / `message:deleted` à la room ET rafraîchissaient l'aperçu de liste, mais n'enfilaient **rien** : un participant hors ligne à cet instant ne l'apprenait jamais — le message supprimé restait visible et le contenu pré-édition restait affiché indéfiniment, jusqu'à un refetch complet fortuit de la conversation. Portée réelle : le SDK iOS édite via `PUT /messages/:messageId` et supprime via `DELETE /conversations/:id/messages/:messageId` (`MessageService.swift`) — les deux en REST. Toute édition/suppression faite depuis l'app iOS divergeait donc en silence de la même action faite en socket depuis le web. L'empreinte de l'oubli était dans la signature elle-même : `MeeshySocketIOManager.enqueueOfflineMessageMutation` (le point d'entrée REST, utilisé par pin/unpin) acceptait déjà `'edited'` — un appelant prévu, jamais écrit — et n'avait pas `'deleted'`. Correctif : un diffuseur unique `broadcastMessageMutation` (`services/gateway/src/socketio/broadcastMessageMutation.ts`) qui adresse les **trois** audiences d'une mutation (room de conversation, rooms `user:<id>` des écrans de liste, file de livraison hors ligne) et par lequel passent désormais les cinq sites REST — ce qui supprime au passage la duplication qui rendait l'asymétrie invisible (aucun des cinq blocs ne référençait les autres) et empêche un sixième transport de rouvrir le trou. Contrat best-effort inchangé : chaque canal est indépendant et une diffusion qui échoue ne transforme jamais une édition déjà commitée en 500.

- **Gateway — un participant débanni restait invisible du temps réel : ses sockets n'étaient JAMAIS remises dans la room de conversation, et il n'apprenait même pas son débannissement** : le bannissement (`services/gateway/src/routes/conversations/ban.ts`) évince explicitement toutes les sockets de la cible de `conversation:<id>` (`io.in(ROOMS.user(target)).fetchSockets()` → `leave`), mais le débannissement — sa transition inverse exacte — ne les y remettait pas. Aucun autre chemin ne le fait : `AuthHandler._joinUserConversations` ne rejoue les joins qu'à la (re)connexion, et les 8 autres sites d'octroi d'appartenance (ajout de participant, lien de partage, invitation, création…) appellent tous `joinUserToConversationRoom` — l'unban était le seul à l'omettre. Conséquence bien pire qu'un simple retard d'affichage : `connectedUsers` rapporte l'utilisateur **EN LIGNE**, si bien que les deux chemins d'envoi (`MessageHandler.broadcastNewMessage` et `MeeshySocketIOManager._broadcastNewMessage`) le **sautent à l'enqueue de la file de livraison hors ligne** — il ne reçoit ni l'émission live (il n'est plus dans la room) ni le replay au reconnect (jamais mis en file). Messages, réactions, éditions, épinglages et accusés émis entre le débannissement et sa prochaine reconnexion étaient donc **perdus purement et simplement**, pas différés — exactement le risque que `AuthHandler` documente quand un join de room échoue. Second défaut, même racine : `conversation:participant-unbanned` n'est diffusé qu'à la room de conversation, celle dont le ban l'avait évincé — la personne débannie était **le seul participant à ne jamais l'apprendre** (le ban, lui, émet AVANT d'évincer, donc le banni reçoit bien le sien). Correctif : `joinUserToConversationRoom(targetUserId, id)` (SSOT partagé avec les 8 autres sites) **awaité AVANT** la diffusion, échec journalisé et non fatal (la diffusion part quand même pour les autres membres). Régressions couvertes (RED→GREEN) dans `services/gateway/src/__tests__/unit/routes/conversations/ban.test.ts` : re-join avec (userId, conversationId) résolus, **ordre** join-puis-émission, et diffusion préservée quand le re-join échoue ; l'ordre inverse du ban (émission-puis-éviction) est désormais verrouillé par un test symétrique. Le mock socket précédent (`mockReturnThis`, aucune assertion) ne pouvait exprimer aucun de ces ordres — d'où la survie du défaut.

- **Web — le compteur de membres dérivait d'un cran vers le bas à chaque cycle bannissement/débannissement** : `use-socket-cache-sync.ts` décrémente `memberCount` sur `conversation:participant-banned` mais son miroir `handleConversationParticipantUnbanned` se contentait d'invalider la liste des participants, sans jamais ré-incrémenter. Avec `staleTime: Infinity` (Socket.IO est la source de vérité, le cache ne se relit pas seul), l'écart persistait jusqu'à un refetch complet sans rapport. iOS applique déjà `memberCount += 1` sur ce même événement (`ConversationListViewModel`) : c'est le web qui divergeait. Correctif : `+1` symétrique du `-1` du bannissement, même idiome que `handleConversationJoined`. Régression couverte (RED→GREEN) dans `apps/web/__tests__/hooks/queries/use-socket-cache-sync.test.tsx` par un aller-retour ban→unban qui doit rendre le compteur inchangé.

- **Web — le suivi de lecture exact n'observait AUCUNE bulle montée après l'ouverture de la conversation : les accusés de lecture ne progressaient plus (et des messages jamais affichés finissaient déclarés lus)** : `useSeenMessages` (`apps/web/hooks/use-seen-messages.ts`) abonne son `IntersectionObserver` aux bulles présentes au montage (`container.querySelectorAll('[id^="message-"]')`, qui descend bien dans le sous-arbre) puis délègue TOUT le reste — liste virtualisée, messages reçus en temps réel — à un `MutationObserver`. Or ses callbacks `attach`/`detach` ne testaient que le **nœud rapporté lui-même** (`messageIdOf(node)` → `node.id.startsWith('message-')`), alors que `MutationObserver` rapporte la **racine** de chaque mutation : `messages-display.tsx` enveloppe chaque `BubbleMessage` dans un `<div key={message.id}>` **sans `id`** (branche virtualisée comme branche simple), et c'est ce wrapper que React insère. La condition ne pouvait donc **jamais** matcher en production — seul le lot initial était observé. Deux conséquences opposées, toutes deux visibles : (1) tout message arrivé APRÈS le premier effet (`message:new`, replay de la delivery-queue, rangée virtualisée entrant à l'écran) n'était jamais observé, donc jamais rapporté au serveur — l'accusé de lecture ✓✓ bleu de l'expéditeur et le badge non-lus du lecteur restaient bloqués ; à froid, si les messages arrivent après le montage de l'effet (dépendances `[containerRef, conversationId, dwellMs, idleMs, resolveLanguage]`, toutes stables), **aucune** bulle n'était observée de toute la session ; (2) symétriquement, une bulle démontée ne recevait jamais son `disappeared` — elle restait « visible » pour `SeenMessageAccumulator` et franchissait le seuil de présence hors écran, déclarant lus des messages que l'utilisateur n'a jamais vus : exactement le défaut par fenêtre temporelle que le suivi exact corrige côté serveur. Correctif : `forEachBubble(node, visit)` applique le traitement au nœud **et à ses descendants** `[id^="message-"]` (un sous-arbre retiré conserve ses descendants, la même descente vaut donc au détachement). Régressions couvertes (RED→GREEN) dans `apps/web/__tests__/hooks/use-seen-messages.test.tsx` : bulle montée dans son wrapper de rangée, sous-arbre à plusieurs bulles, désabonnement au retrait du wrapper, et le cas comportemental « une bulle sortie du DOM avant le seuil n'est pas déclarée lue » (RED : `markAsRead` appelé avec l'id). Les tests existants encodaient la forme DOM que la production ne produit jamais (bulle insérée en nœud direct), d'où la survie du défaut. Suite `__tests__/hooks` : 106 suites / 2105 tests vertes. @see `docs/superpowers/specs/2026-07-24-read-exactness-design.md`

- **Web — un message dont le renvoi automatique échouait était SUPPRIMÉ de la file d'échec au lieu d'y être conservé : perte définitive, sans trace UI, dès le 1er essai raté** : `useAutoRetryFailedMessages` (`apps/web/hooks/use-auto-retry-failed-messages.ts`) enveloppait `meeshySocketIOService.sendMessage` dans un `try/catch` et appelait `store.removeFailedMessage(msg.id)` dans le `try`, en **ignorant la valeur retournée**. Or ce service ne rejette sur **aucun** chemin : socket absent, ACK expiré (`timedOut`), file de l'orchestrateur pleine ou expirée, échec de chiffrement et erreurs serveur résolvent tous `{ success: false }` (`services/socketio/messaging.service.ts`, `services/socketio/orchestrator.service.ts`). Une promesse résolue ne prouvait donc rien, et le `catch` — seul endroit qui conservait l'entrée et posait `Max retries exceeded` — était du **code mort** : au premier essai raté l'entrée quittait la file (qui pilote l'affichage « échec »), rendant `MAX_RETRY_COUNT = 3` purement décoratif puisqu'un 2e essai n'avait plus d'objet à rejouer. Correctif : la livraison est lue sur `ack.success`, comme le faisait déjà le renvoi MANUEL (`ConversationLayout.handleRetryFailedMessage`, `result?.success ?? false`) — c'était un trou de parité entre les deux chemins, pas un arbitrage de design. Une rejection inattendue est traitée comme un échec au lieu d'avorter la file entière.

- **Web — la file de renvoi hors-ligne n'était jamais vidée à la reconnexion du socket, et une file restaurée depuis localStorage ne repartait jamais de toute la session** : le même hook ne dépendait que de `isOnline` (`navigator.onLine`) alors que sa garde réelle, `getConnectionDiagnostics().isConnected`, était lue **impérativement** donc non réactive. Au retour du réseau, l'événement `online` précède de plusieurs secondes le handshake Socket.IO : l'effet se déclenchait, trouvait le socket encore déconnecté, sortait — et plus aucune dépendance ne changeait pour le relancer. Même trou au démarrage à froid, où `isOnline` vaut déjà `true` au montage. La garde ne pouvait structurellement être évaluée qu'au mauvais moment. Correctif : le déclencheur devient `useConnectionStatus().isReady` (`isOnline && isSocketConnected`), déjà déclarée source unique de vérité de cet état, ce qui supprime du même coup la lecture impérative dupliquée.

- **Web — un clignotement de la connexion pendant un renvoi en cours démarrait une SECONDE boucle sur les mêmes messages (doubles envois, `retryCount` doublement incrémenté)** : le cleanup de l'effet remettait `isRetrying.current = false` sans pouvoir savoir si la boucle planifiée avait déjà démarré — et `clearTimeout` n'interrompt pas une boucle qui attend un ACK. Un re-run de l'effet repassait alors la garde et rejouait le même instantané. Correctif : jeton de possession libéré par la boucle elle-même (le cleanup ne peut libérer qu'un run non démarré) ; la disponibilité est relue depuis une ref à chaque itération, de sorte qu'un renvoi interrompu par une coupure s'arrête au lieu de brûler le budget de réessai des messages restants sur des envois voués à l'échec ; un run interrompu ré-arme l'effet pour confier le reliquat à un run neuf.

- **Web — le rattrapage après reconnexion/refocus (`syncNewerMessages`) ancrait sa borne `after` sur un message OPTIMISTE, donc sur l'horloge LOCALE : tous les messages reçus pendant la coupure étaient silencieusement sautés** : `useConversationMessagesRQ` (`apps/web/hooks/queries/use-conversation-messages-rq.ts`) calculait le watermark de rattrapage par `newestCreatedAtMs(cached.pages.flatMap(p => p.messages))` — **tous** les messages du cache, y compris les optimistes, dont le `createdAt` est posé par `createOptimisticMessage` avec l'horloge de l'appareil au moment de la saisie. Or le seul moment où un message optimiste séjourne dans le cache est précisément celui où le rattrapage sert : composer hors-ligne (file d'attente) ou perdre l'ACK d'un envoi. Le client demandait alors au gateway `createdAt > maintenant-sur-cet-appareil` — et le gateway, qui compare en temps SERVEUR, ne renvoyait rien : tout ce que les pairs avaient envoyé pendant la coupure restait invisible jusqu'à un rechargement à froid. Une horloge locale en avance élargissait la fenêtre perdue d'autant. Correctif : le watermark est calculé **uniquement sur les messages confirmés par le serveur** (`!isOptimisticMessage`) — exactement le contrat déjà appliqué côté iOS par `SyncWatermark.newest` (`packages/MeeshySDK/Sources/MeeshySDK/Models/SyncWatermark.swift`), dont le web était la seule surface à diverger. Quand le cache ne contient AUCUN message serveur (conversation dont tout le contenu a été composé hors-ligne), repli sur la relecture complète — non destructive, `mergePendingLocalMessages` préserve les envois en attente — au lieu d'un abandon silencieux.
- **Web — un message partageant la milliseconde exacte du dernier message en cache n'était rattrapable par AUCUNE synchronisation** : le paramètre `after` est appliqué par le gateway en filtre **strict** `createdAt > after` (`buildAfterWatermarkClause`, `services/gateway/src/routes/conversations/messages.ts`). En ancrant la requête sur l'instant exact du plus récent message connu, un jumeau créé dans la même milliseconde (rafale de groupe, envoi agent/bot) tombait hors fenêtre à chaque tentative et restait perdu jusqu'au rechargement à froid. Correctif : reculer la borne d'une milliseconde (`WATERMARK_INCLUSIVE_MARGIN_MS`) pour rendre la fenêtre inclusive — le message frontière revient et est absorbé par la déduplication par id déjà en place. Même parade que côté iOS (`ConversationViewModel.syncMissedMessages`, `cursor = newestLocal.addingTimeInterval(-0.001)`).
- **Web — le rattrapage dupliquait visuellement un envoi dont l'ACK avait été perdu pendant la coupure** : `syncNewerMessages` ne dédupliquait que par `id`. La copie serveur d'un envoi confirmé pendant la déconnexion porte un `id` MongoDB différent du `_tempId` (`cid_<uuid>`) de la bulle optimiste, mais bien le `clientMessageId` que le client a généré — que la route REST expose déjà. Résultat : la bulle optimiste « en cours d'envoi » restait à côté de sa propre copie serveur, l'expéditeur voyant son message deux fois jusqu'au prochain chargement à froid. Correctif : le rattrapage réconcilie par `clientMessageId` et **remplace** l'entrée optimiste confirmée au lieu de la juxtaposer (même contrat que `mergePendingLocalMessages` sur la relecture de page). Régressions couvertes (RED→GREEN) : 4 tests dans `apps/web/__tests__/hooks/queries/use-conversation-messages-rq.test.tsx` (watermark ignorant les optimistes, repli relecture complète, fenêtre inclusive à la milliseconde, réconciliation par `clientMessageId`). Suite web complète verte.
- **`reaction:add` / `reaction:remove` (chemin WebSocket temps réel) répondaient `{ success: false }` alors que la réaction était DÉJÀ persistée quand une lecture d'agrégation post-écriture échouait — rollback optimiste du client + aucun broadcast aux pairs** : `ReactionHandler.handleReactionAdd` et `handleReactionRemove` (`services/gateway/src/socketio/handlers/ReactionHandler.ts`) committaient d'abord la mutation DB (`addReaction`/`removeReaction`), mais n'envoyaient l'ACK de succès qu'**après** une lecture d'agrégation supplémentaire awaitée (`createUpdateEvent → getEmojiAggregation`, une requête DB) et, sur le chemin add, un `message.findUnique` de plus. Si l'une de ces lectures throwait (charge/timeout transitoire — plausible à l'échelle 100k+ msg/s de la plateforme), le contrôle tombait dans le `catch` externe, qui répondait `{ success: false }` — **alors que la réaction était déjà en base**. Scénario réel : Alice tape 👍 → `addReaction` upsert la réaction (la DB l'a) → `getEmojiAggregation` throw sur une erreur transitoire → le client reçoit `{ success: false }`, **annule** sa réaction optimiste (n'affichant plus aucun 👍, ou sur remove **ré-affichant** une réaction pourtant supprimée), et **aucun `REACTION_ADDED`/`REACTION_REMOVED` n'est diffusé** à quiconque : le réacteur et tous les pairs restent incohérents avec la DB jusqu'au prochain `reaction:sync`. Cela contredisait l'intention documentée du chemin add lui-même (« Fire-and-forget post-success side-effects so errors in broadcast or notification do not confuse the already-confirmed client response ») et le repli dégradé qu'il applique déjà à la suppression d'emoji **remplacé** — mais pas à l'événement **primaire** qui gate l'ACK ; le chemin remove n'avait aucun repli. Correctif : envoyer l'ACK de succès dès l'écriture confirmée, puis exécuter la résolution de conversation, la lecture d'agrégation, le broadcast et l'enqueue offline en effets de bord fire-and-forget **enveloppés dans leur propre try/catch** — une lecture post-écriture ratée ne peut donc ni faire basculer l'ACK en échec ni atteindre le catch externe (qui double-invoquerait le callback). Le timing du broadcast sur le chemin sain est inchangé (l'agrégation résout toujours avant le broadcast) ; le chemin add n'émet plus la lecture d'agrégation gaspillée quand le message est introuvable. Régression couverte par tests (RED→GREEN) : `ReactionHandler.test.ts` → add « replies success (not failure) when the post-write aggregation read throws — reaction already persisted » + remove « … reaction already removed » (RED avant : `{ success: false, error: 'aggregation read timeout' }`). Suite `ReactionHandler` 53/53, handlers socketio 549/549, `tsc --noEmit` clean.
- **Message affiché en DOUBLE après l'expiration du ACK d'envoi — la déduplication du cache socket ne réconciliait que les optimistes en statut `'sending'`, jamais `'failed'`** : `useSocketCacheSync` (`apps/web/hooks/queries/use-socket-cache-sync.ts`) réconcilie une bulle optimiste avec le message serveur diffusé via deux voies — dédup par `_serverMessageId` (posé par un ACK réussi) et, en repli, dédup par timestamp bornée à 5 s. Le repli était gardé par `m._localStatus === 'sending'`, excluant l'état `'failed'`. Or cet état est produit délibérément par la couche d'envoi : sur timeout du ACK (10 s), `messaging.service` retourne `{ timedOut }` **sans** repli REST (« message:new may still arrive ») et `markMessageFailed` bascule la bulle en `'failed'` **sans** poser `_serverMessageId`. Scénario réel : sur une connexion lente, un envoi est **persisté et diffusé** côté serveur, mais le ACK n'arrive pas sous 10 s → la bulle devient `'failed'` (bouton retry affiché) ; puis le `message:new` arrive — typiquement au **replay de la delivery-queue au reconnect**, bien après le timeout. Aucune des deux voies de dédup ne matche (id `cid_…` ≠ ObjectId ; `_serverMessageId` non posé ; la voie timestamp exige `'sending'`) → le message serveur est ajouté comme neuf : l'utilisateur voit son message **deux fois** (une bulle en échec **et** la version livrée ; presser retry forge alors un nouveau `cid` et crée un doublon **côté serveur** aussi). Correctif : élargir le repli à **tout optimiste non encore réconcilié** (`_localStatus` vaut exactement `'sending' | 'failed'`) — la fenêtre `createdAt` de 5 s continue de protéger contre le match d'un message sans rapport, et un broadcast qui matche (même auteur, < 5 s) **prouve** que l'envoi a réussi : la bulle en échec est réconciliée en le message livré, jamais dupliquée. Régression couverte par tests (RED→GREEN) : `use-socket-cache-sync.test.ts` → « reconciles a timed-out (failed) optimistic message when the server broadcast arrives » (RED avant : `messages.length === 2`). Suite hooks/queries 47/47, fichiers modifiés `tsc` clean.
- **La détection de présence de l'e-mail immédiat haute priorité interrogeait un room Socket.IO INEXISTANT — tout utilisateur EN LIGNE était classé « hors ligne » et bombardé d'e-mails transactionnels (mentions, appels manqués, alertes de sécurité)** : dans `NotificationService.createNotification` (`services/gateway/src/services/notifications/NotificationService.ts`), la branche « envoi immédiat pour notifications haute priorité aux utilisateurs hors ligne » testait la présence via `io.in(params.userId).fetchSockets()` — le room nommé par l'**id brut** de l'utilisateur (`"665abc…"`). Correctif : `broadcastNewMessage` résout désormais `validatedMentions` (String[] de usernames) en `User.id` via le helper existant `_resolveMentionUserIds` (échec de lookup avalé — ne bloque jamais le broadcast) et émet `mention:created` vers chaque `user:<id>`, en excluant l'expéditeur (garde anti auto-mention sur `senderUserId`, `null` pour les anonymes). Parité stricte avec le writer REST. Régression couverte par tests (RED→GREEN) : `MessageHandler.test.ts` → « emits mention:created to each mentioned user's personal room » + garde auto-mention.
- **Blocage/déblocage d'un utilisateur en DM sans effet pendant jusqu'à 5 min (contournement du blocage)** : le gate d'envoi `_isDirectMessageBlocked` met en cache le résultat de blocage bidirectionnel sous une clé SYMÉTRIQUE `blocks:<sorted(a,b)>` pendant 300s, mais les routes `POST`/`DELETE /users/:id/block` ne l'invalidaient jamais. Scénario de contournement : A et B échangent (cache `= '0'`), A bloque B, puis B envoie un message dans les 300s → hit cache `'0'` → le message de B **est délivré à A malgré le blocage**. Symétriquement, un déblocage laissait B rejeté avec `USER_BLOCKED` pendant 5 min. Correctif : les deux routes invalident désormais la clé symétrique (`getCacheStore().del(blockCacheKey(...))`, best-effort) après le write DB. Format de clé factorisé dans un helper partagé `utils/block-cache.ts` (`blockCacheKey`, `BLOCK_CACHE_TTL_SECONDS`) pour que le site d'écriture (send-gate) et les sites d'invalidation ne puissent plus diverger. Régression couverte par tests (RED→GREEN) : `blocking.test.ts` → invalidation sur block **et** unblock.
- **Aperçu de conversation figé sur l'écran liste après édition/suppression du dernier message** : `broadcastNewMessage` fanne `conversation:updated` (portant `lastMessageId`/`lastMessagePreview`) vers chaque salle personnelle `user:<id>` à l'envoi — précisément parce qu'un participant posé sur la liste de conversations a quitté la salle `conversation:<id>` mais reste dans `user:<id>`. L'édition et la suppression, elles, n'émettaient `message:edited`/`message:deleted` que vers `conversation:<id>` : un membre en ligne posé sur la liste (jamais entré dans la conversation cette session) ne recevait donc aucun signal quand le **dernier** message était édité ou supprimé, et sa ligne continuait d'afficher le texte pré-édition (ou le message supprimé) jusqu'à réouverture (refetch SWR). Le handler delete recalculait pourtant déjà `lastMessageAt` — le serveur *savait* que l'aperçu avait changé. Correctif : helper partagé `emitConversationPreviewUpdate` qui recalcule le dernier message non supprimé et fanne `conversation:updated` vers chaque salle user de participant actif (anonymes ignorés, dédup par userId), appelé après chaque émission `message:edited`/`message:deleted` sur les 7 sites (WS `MessageHandler` + REST `messages.ts` + `messages-advanced.ts`) — pas de dérive par transport. Best-effort : ne fait jamais échouer l'edit/delete. Éditer/supprimer un message non-dernier émet l'aperçu inchangé (no-op idempotent client). Régression couverte par tests (RED→GREEN) : `emitConversationPreviewUpdate.test.ts` (5 tests) + `MessageHandlerEditDelete.test.ts`.
- **`message:new.senderId` émis en Participant.id sur le chemin WS `message:send` (vs User.id sur REST/ZMQ) — auto-message multi-device jamais réconcilié** : `Message.senderId` est un `Participant.id` (relation Prisma `MessageSender`). Le writer REST/ZMQ (`MeeshySocketIOManager.broadcastMessage`) le résolvait déjà vers le `User.id` (« les clients comparent senderId avec leur userId »), mais le writer WS (`MessageHandler._buildMessagePayload`) émettait le `Participant.id` brut. Côté client, `use-socket-cache-sync.ts` compare `message.senderId === currentUser.id` (un `User.id`) pour détecter ses propres messages et promouvoir l'optimistic bubble multi-device — sur le chemin WS le test échouait toujours (Participant.id ≠ User.id), donc l'auteur voyait son propre message en double / rendu comme entrant. Invisible sur REST (qui résolvait correctement) : seul le transport WS était atteint. Correctif : `_buildMessagePayload` résout désormais `senderId` avec la même chaîne `participant.userId ?? participant.user?.id ?? message.senderId` que les writers REST/ZMQ (fallback Participant.id pour les anonymes). Le champ `sender.id` (Participant.id) reste disponible séparément ; `conversation:updated` garde volontairement le Participant.id brut (cohérent entre ses deux writers). Régression couverte par test (RED→GREEN) : `MessageHandler.test.ts` → « exposes the sender User.id (not Participant.id) in the message:new senderId ».
- **Événements temps réel `_seq` émis dans le désordre sous concurrence (SyncEngine)** : `emitWithSeq` allouait le numéro de séquence monotone via `await sequenceService.nextSeq(userId)` puis émettait immédiatement. `nextSeq` fait un `upsert{increment}` Mongo, atomique au niveau document (valeurs distinctes et gapless **dans l'ordre d'appel**) — mais deux appels concurrents pour le même user s'exécutent sur des connexions poolées différentes dont les réponses peuvent revenir **dans le désordre** : le `await` de `_seq=N+1` pouvait résoudre avant celui de `_seq=N`, émettant l'événement le plus récent en premier. Le client SyncEngine avance alors `lastSeq` à `N+1` et rejette le `_seq=N` reçu ensuite comme doublon périmé → perte d'une `notification:new` temps réel (deux expéditeurs écrivant au même destinataire quasi-simultanément), récupérée seulement au prochain `/sync`. Cela violait le contrat « séquence monotone pour détection de gap exacte » que le module documente. Correctif : l'allocation du `_seq` **et** l'emit sont désormais sérialisés **par user** via une chaîne de promesses en mémoire (`Map<userId, Promise>`), garantissant « ordre d'émission == ordre d'allocation » ; les users distincts gardent des chaînes séparées (aucun head-of-line blocking cross-user) et la Map est purgée une fois chaque chaîne drainée. Résilience préservée : un échec d'allocation émet toujours sans `_seq`, un échec d'emit ne casse pas la chaîne du user. Régression couverte par test (RED→GREEN) : `emitWithSeq.test.ts` → « emits _seq in strictly monotonic order even when nextSeq resolutions race » + garde anti-blocage cross-user.
- **Badge de non-lus jamais mis à jour en temps réel pour les utilisateurs anonymes** : à l'authentification, le socket anonyme rejoignait la salle personnelle nue `<participantId>` (`socket.join(socketUser.id)`), alors que le chemin JWT — et **tous** les émetteurs d'événements personnels (`CONVERSATION_UNREAD_UPDATED`, mentions, etc.) — adressent `io.to(ROOMS.user(participant.userId ?? participant.id))`, soit `user:<participantId>` pour un anonyme. Le socket anonyme était donc dans une salle qu'aucun émetteur ne cible : quand un message arrivait dans une conversation qu'il n'avait pas ouverte, `conversation:unread-updated` était émis vers `user:<participantId>` et silencieusement perdu ; le compteur de non-lus restait figé jusqu'à un refetch REST manuel. Le repli `?? participant.id` présent dans les deux sites d'émission (WS `_updateUnreadCounts` et REST `broadcastMessage`) montrait l'intention explicite de servir les anonymes — la livraison échouait par simple divergence salle-de-jointure vs salle-d'émission. Correctif : le chemin anonyme rejoint désormais `ROOMS.user(socketUser.id)`, alignant jointure et émission sur la convention unique (`AuthHandler._authenticateAnonymousUser`). Aucun émetteur ne ciblait la salle nue (vérifié par balayage de tous les `io.to(...)`/`io.in(...)` du gateway), donc zéro régression. Régression couverte par test (RED→GREEN) : `AuthHandler.test.ts` → « joins the anonymous socket to the ROOMS.user personal room emitters target ».
- **Mentions d'utilisateurs à casse mixte silencieusement perdues** : `resolveMentionedUsers` (source des `mentionedUsers` du broadcast temps réel `message:new`, du chemin REST d'envoi, et du rendu des mentions posts/commentaires/feed) interrogeait `prisma.user.findMany` avec `username: { in: [...], mode: 'insensitive' }`. Or MongoDB ignore `mode: 'insensitive'` combiné à `in` (déjà documenté dans `MentionService.resolveUsernames`), donc la correspondance était sensible à la casse contre des handles préalablement mis en minuscules — une mention `@Alice_B` (username stocké `Alice_B`) ne résolvait rien : la puce de mention, la surbrillance et le lien profond disparaissaient pour tous les destinataires, et la notification « vous avez été mentionné·e » ne se déclenchait jamais. Correctif : `OR` + `equals` insensible à la casse (une clause par handle), le motif déjà utilisé par `resolveUsernames`. Régression couverte par tests (RED→GREEN) émulant la sémantique Prisma+MongoDB.
- **Réactions dupliquées en cas de course concurrente** : `ReactionService.addReaction` appliquait le modèle "1 emoji par user" au niveau applicatif (find/deleteMany/create), non atomique — deux ajouts concurrents avec des emojis différents pouvaient chacun insérer leur propre ligne. Passage à un `upsert` atomique sur la clé composite `(messageId, participantId)` (l'index unique ne porte plus sur l'emoji). Migration Mongo requise avant déploiement : `packages/shared/prisma/migrations/2026-07-04-reaction-single-per-user-unique-index.mongodb.js`. Voir `docs/analyses/2026-07-04-reaction-duplicate-race-fix.md`.
- **Idem pour les réactions par pièce jointe** : `AttachmentReactionService.addAttachmentReaction` portait exactement la même course (findMany/deleteMany/upsert non atomique). Même correctif — `upsert` atomique sur `(attachmentId, participantId)`, index resserré. Migration Mongo requise avant déploiement : `packages/shared/prisma/migrations/2026-07-04-attachment-reaction-single-per-user-unique-index.mongodb.js`. Voir `docs/analyses/2026-07-04-attachment-reaction-duplicate-race-fix.md`.

### 🎉 Refonte Majeure - Système de Notifications

#### Changed

- **Structure groupée** : Réorganisation complète de l'architecture des notifications en groupes logiques (CORE, ACTOR, CONTEXT, METADATA, STATE, DELIVERY)
- **Suppression du champ `title`** : Le title est maintenant construit dynamiquement côté frontend via i18n pour un meilleur support multilingue
- **`data` → `metadata`** : Remplacement du champ Json non typé par un système de discriminated unions TypeScript fortement typé
- **Champs dénormalisés déplacés** : `senderId`, `senderUsername`, etc. regroupés dans `actor`
- **État groupé** : `isRead`, `readAt`, `createdAt` déplacés dans le groupe `state`
- **Context enrichi** : Informations de contexte (conversation, message, appel) regroupées dans `context`

#### Added

- **Nouveau groupe `actor`** : Informations sur l'utilisateur qui a déclenché la notification (id, username, displayName, avatar)
- **Nouveau groupe `context`** : Informations contextuelles (conversationId, conversationTitle, conversationType, messageId, callSessionId, etc.)
- **Nouveau groupe `metadata`** : Données type-spécifiques avec typage fort via discriminated unions
- **Nouveau groupe `state`** : État de lecture et timestamps (isRead, readAt, createdAt, expiresAt)
- **Nouveau groupe `delivery`** : Suivi multi-canal (emailSent, pushSent)
- **Champ `priority`** : Niveaux de priorité (low, normal, high, urgent)
- **Helper `buildNotificationTitle()`** : Construction dynamique des titles avec support i18n
- **Type guards** : Fonctions pour typer correctement le metadata selon le type de notification
- **NotificationService refactorisé** : API simplifiée avec méthodes spécifiques par type (`createMessageNotification`, `createMentionNotification`, etc.)
- **NotificationFormatter** : Formatage cohérent DB → API
- **Socket.IO mis à jour** : Émission d'événements `notification:new` avec structure groupée
- **Documentation complète** :
  - `docs/notifications/STRUCTURE.md` : Architecture détaillée avec exemples
  - `docs/notifications/MIGRATION_GUIDE.md` : Guide de migration complet

#### Removed

- **Champ `title`** : ❌ Plus stocké en DB, construit dynamiquement
- **Champs dénormalisés à la racine** : ❌ `senderId`, `senderUsername`, `senderAvatar`, `senderDisplayName`
- **Références directes** : ❌ `conversationId`, `messageId`, `callSessionId` à la racine
- **Champ `data` non typé** : ❌ Remplacé par `metadata` structuré
- **Champs d'état à la racine** : ❌ `isRead`, `readAt` déplacés dans `state`

#### Breaking Changes
