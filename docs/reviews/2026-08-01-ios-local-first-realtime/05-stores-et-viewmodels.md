# 05 — Stores et ViewModels

> Périmètre : propagation multi-vues (stores SDK, cache multi-clés, stores GRDB app-side) et conformité cache-first écran par écran (27 ViewModels de `apps/ios/Meeshy/Features/Main/ViewModels/` + `NotificationListViewModel` logé dans `MeeshyUI`). Méthodologie et sévérités : voir README.md. Architecture de référence : 00-etat-des-lieux.md. HEAD audité : 901e92589.

## Rappel d'architecture (renvoi à 00-etat-des-lieux.md, §2-4)

Trois familles de « stores » coexistent : (1) les stores SDK (`ConversationStore` — SSOT exemplaire avec outbox durable, versioning et rollback — et `UserCategoryStore`) ; (2) le cache unifié `CacheCoordinator`/`GRDBCacheStore`, où un même post vit sous plusieurs clés (`main-feed`, `<postId>`, `bookmarks`, `user:<id>`) et où `patchEverywhere` balaie L1 ∪ L2 ; (3) les stores GRDB app-side (`MessageStore`, réellement branché au rendu et robuste ; `FeedStore`/`CommentStore`, écrits mais jamais rendus). Les ViewModels composent ces couches selon la discipline `CacheResult` (`.fresh/.stale/.expired/.empty`) ; les écrans étalons sont `ConversationListViewModel` (4 cas gérés, récupération `.expired` via `loadIgnoringExpiry`) et `ConversationViewModel` (publication atomique messages + métadonnées). Les compteurs sont absolus (recalculés gateway) : deux surfaces ne peuvent pas dériver **tant que l'événement socket arrive** — c'est précisément cette réception qui est fragilisée par plusieurs écarts ci-dessous.

## Écarts retenus

### stores-05 — Double pipeline de persistance feed : tables `feed_posts`/`feed_comments` write-only (rendu mort) et JAMAIS purgées au logout · **P1** · effort M
**Constat.** Le pipeline GRDB du feed (FeedSocketHandler → FeedPersistenceActor → tables `feed_posts`/`feed_comments`) est alimenté en continu mais son unique chemin de lecture est désactivé, et aucune purge au logout n'existe pour ces tables. **Preuve.** Rendu mort : `FeedView.swift:56` `@State private var useUIKitList = false`, unique lecture ligne 530, jamais togglé (grep monorepo) ; `PostDetailView.swift:695-699` crée un `CommentStore` et appelle `loadInitial()`, mais la vue rend `viewModel.topLevelComments` (ligne 460, source CacheCoordinator) — aucun autre `commentStore.` lu. Écritures actives des deux côtés : `FeedSocketHandler` entier, `FeedViewModel.swift:187-193`, `PostDetailViewModel.swift:149-153`, `NSEPendingPostConsumer.swift:123-134`.
**Impact.** Les posts et commentaires FRIENDS/ONLY de l'utilisateur A restent en base App Group sous la session de l'utilisateur B : fuite cross-compte au repos (P1 et non P0 car aucun chemin de lecture actif ne l'expose aujourd'hui). ### stores-02 — `feed:subscribe` jamais ré-émis au retour sur le feed (socket déjà connecté) → temps réel feed + `patchEverywhere` morts après le premier aller-retour · **P1** · effort S
**Constat.** À la sortie du feed, le client quitte la room feed côté gateway ; au retour, seul `connect()` est rappelé — or il early-return si le socket est déjà connecté, et `subscribeFeed()` n'est émis que dans le handler `.connect`. La room n'est donc jamais re-jointe sans flap réseau.
**Preuve.** Chaîne complète vérifiée : sortie feed → `unsubscribeFromSocketEvents` (`FeedViewModel.swift:1171-1175`, déclenché par `onDisappear`, `FeedView.swift:1190-1191`) → emit `feed:unsubscribe` → gateway `socket.leave(ROOMS.feed(userId))` (`SocialEventsHandler.ts:165-169`). Retour → `.task` (`FeedView.swift:1108`) → `subscribeToSocketEvents` (ligne 944) → guard `socketCancellables.isEmpty` (ligne 951, passe car vidé par `removeAll`) → `socialSocket.connect()` (ligne 952) qui early-return si `.connected || .connecting` (`SocialSocketManager.swift:441-443`). `subscribeFeed()` n'est émis QUE dans le handler `.connect` (ligne 846) — grep monorepo : aucun autre site d'émission. `post:created`/`liked`/`bookmarked`/`comment:added` sont broadcastés vers `ROOMS.feed` (`SocialEventsHandler.ts:124, 392`).
**Impact.** Après un simple aller-retour feed → conversation → feed sans coupure réseau, plus aucun événement social n'arrive : les sinks du ViewModel ET `CacheCoordinator.applyPostLike` (`CacheCoordinator.swift:427-449`, même publisher) sont affamés — RAM et cache dérivent jusqu'au prochain reconnect.
**Correctif pas-à-pas.**
1. `FeedViewModel.swift`, dans `subscribeToSocketEvents` : insérer `socialSocket.subscribeFeed()` immédiatement après `socialSocket.connect()` (ligne 952) — APRÈS le guard de la ligne 951, pour rester apparié au ré-armement des sinks. L'émission est idempotente : le join d'une room déjà jointe est un no-op Socket.IO ; si le socket n'est pas connecté, l'émission est perdue mais rejouée par le handler `.connect` (ligne 846).
2. AUCUN changement de protocole ni de mock : `subscribeFeed()` est déjà sur `SocialSocketProviding` (`SocialSocketManager.swift:279`) et `MockSocialSocket` trace déjà `subscribeFeedCallCount` (`MockSocialSocket.swift:55, 72-73`).
3. Ne PAS toucher au handler `.connect` ni au gateway.
**Tests (TDD — RED d'abord).** Dans `apps/ios/MeeshyTests/Unit/ViewModels/FeedViewModelTests.swift` (`@MainActor`, `makeSUT` avec `MockSocialSocket` injecté) : `test_subscribeToSocketEvents_afterUnsubscribe_reemitsFeedSubscribe` — subscribe → unsubscribe → subscribe, asserter `subscribeFeedCallCount == 2` (en delta, jamais en absolu) ; `test_unsubscribeFromSocketEvents_always_emitsFeedUnsubscribe` — `unsubscribeFeedCallCount == 1`.
**Risque de régression.** Nul (double join absorbé par `socket.join`). Complémentaire de rts-01 (fichier 03) : le re-join couvre le flux temps réel, la revalidation au retour couvre le trou pendant l'absence — les deux sont nécessaires.

### stores-06 — Mutation optimiste de prefs (pin/mute/archive/read) jamais persistée en L2 par elle-même — perdue visuellement au cold start · **P2** · effort S
**Constat.** Le merge du snapshot `ConversationStore` dans la liste réécrit `conversations` sans jamais programmer la persistance du blob « list » ; la mutation optimiste ne devient durable que si un AUTRE événement déclenche `schedulePersist`.
**Preuve.** `mergeUserStateFromStore` (`ConversationListViewModel.swift:624-636`) réécrit `conversations` sans `schedulePersist` ; `ConversationStore.commit` (lignes 549-553) est RAM + subjects seulement ; `schedulePersist` (lignes 225-246) n'est appelé par aucun des deux. Nuance vérifiée qui borne l'impact sans l'annuler : le sink socket direct `userPreferencesUpdated` (lignes 688-707) appelle `schedulePersist` ligne 707 — donc ONLINE avec écho, la mutation finit persistée. Le trou réel : kill avant l'écho, écho non délivré, et tout le mode offline.
**Impact.** Pin/mute/markRead optimiste → kill de l'app → relaunch : la liste peint l'état PRÉ-mutation depuis le cache (offline : jusqu'au reconnect), alors que l'outbox rejouera bien côté serveur — l'UI locale ment. Violation « Optimistic Updates durables ».
**Correctif pas-à-pas.**
1. `ConversationListViewModel.swift`, fin de `mergeUserStateFromStore` (ligne 635) : remplacer `if changed { conversations = updated }` par `if changed { conversations = updated; schedulePersist() }`.
2. Rien d'autre : le debounce 200 ms (ligne 225) coalesce les rafales, et le persist écrit le cache (pas le store), donc aucune boucle possible.
3. Ne PAS ajouter de persist dans `ConversationStore.commit` : le SDK ne connaît pas la clé « list » du ViewModel — violation SDK purity.
**Tests (TDD — RED d'abord).** Dans `apps/ios/MeeshyTests/Unit/ViewModels/ConversationListViewModelTests.swift` : `test_storeUserStateChange_mergedIntoList_schedulesPersist` — seed du VM avec 1 conversation, capturer `persistCallCount` (DEBUG), pousser un snapshot du store (publisher injecté / `ConversationStore` de test) avec `isPinned` flippé, attendre > 200 ms (`XCTestExpectation`), asserter que `persistCallCount` a augmenté de 1 (delta, jamais absolu) ; `test_storeUserStateEcho_unchangedState_doesNotPersist` — même snapshot inchangé → delta 0 (garde `changed`).
**Risque de régression.** Écritures GRDB un peu plus fréquentes, bornées par le debounce ; la coalescence est assertée via `persistCallCount`.
**Dépendances.** aucune · **Backend requis :** non
