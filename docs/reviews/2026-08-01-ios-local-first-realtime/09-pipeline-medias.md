# 09 — Pipeline médias (téléchargements, cache disque, uploads résumables)

> Périmètre : téléchargement et cache disque des médias (images, audio, vidéo), politique d'auto-téléchargement, prefetch conversation/feed/stories, pins de relecture offline, uploads TUS résumables, seed du cache auteur, purge logout. Méthodologie et sévérités : voir README.md. Architecture de référence : 00-etat-des-lieux.md. HEAD audité : 901e92589.

## Rappel d'architecture

Le cache binaire est porté par `DiskCacheStore` (acteur SDK, L1 NSCache + L2 fichiers clés `SHA256(url)`, quatre instances typées via `CacheCoordinator` : images 300 Mo, audio 200 Mo, vidéo 1 Go, thumbnails 150 Mo). Le téléchargement passe soit par le « funnel » du store (`networkData`, une seule requête par clé, awaiters coalescés), soit par `AttachmentDownloader` app-side (badge de progression) qui s'enregistre dans ce même funnel. L'auto-téléchargement est décidé par `MediaDownloadPolicyEngine` × `NetworkConditionMonitor` × `MediaDownloadPreferencesStore`. L'upload passe par `TusUploadManager` (chunks 10 Mo, checkpoints GRDB par sha256, reprise via l'outbox) puis seed le cache auteur. L'envoi avec pièces jointes suit le plan décrit en 00-etat-des-lieux.md §3 (insert optimiste GRDB, write-ahead offline, TUS en ligne, adoption ACK). Les forces constatées (funnel dédupliqué, LRU par accès réel, pins bornés, purge sélective honnête) sont détaillées dans 00-etat-des-lieux.md — elles ne sont pas remises en cause ici.

### media-01 — Kill pendant un upload EN LIGNE : retry mort + média potentiellement perdu · **P1** · effort M
**Constat.** Le chemin d'envoi en ligne n'écrit aucun record outbox avant l'upload TUS : l'enfilage n'existe que dans le `catch` d'échec, jamais traversé quand l'app est tuée en plein upload. Au relaunch, la bulle est démotie `.failed`, mais le bouton « Réessayer » est un no-op silencieux : le retry média passe exclusivement par l'outbox, qui ne trouve aucune row.
**Preuve.** `ConversationView+AttachmentHandlers.swift:342-414` : le chemin en ligne ne crée aucun record outbox (l'enqueue n'existe que dans le catch `:429-459`). `ConversationViewModel.swift:2877-2892` route le retry média exclusivement via `offlineQueue.retryByClientMessageId`, dont le guard `OfflineQueue.swift:812-814` jette `itemNotFound`, avalé par le catch `:2888-2890` (log uniquement). `reconcileOrphanedSendingRows` (`MessagePersistenceActor.swift:464-508`, appelé par `ConversationViewModel.swift:1449`) démote bien en `.failed` après 120 s les rows `.sending` sans outbox vivant. **Impact.** Photo, vidéo ou vocal envoyé pendant que l'app est tuée en plein upload : bulle `.failed` dont le retry ne fait jamais rien ; comme les fichiers source sont en tmp purgeable, le média peut être définitivement perdu.

Dans le catch (`:415-468`) : SUPPRIMER les re-enqueues `:429-459` — la row write-ahead existe déjà ; un second enqueue créerait une row dupliquée pour le même cmid (`retryByClientMessageId` prend la plus récente et `cancelPendingSend` n'en supprime qu'une → rows fantômes). **Tests (TDD — RED d'abord).** SDK (`packages/MeeshySDK/Tests/MeeshySDKTests/Persistence/OfflineQueueTests.swift`) : `test_enqueueMedia_pendingRowExistsForCmid_isIdempotentNoDuplicate` ; `test_cancelPendingSend_pendingWriteAheadRow_deletesIt` (vérifier s'il existe déjà avant de l'écrire). ### media-03 — Téléchargements non structurés : full-buffer mémoire + itération par octet, pas de reprise · **P2** · effort L
**Constat.** Le téléchargeur app accumule tout le média en mémoire et itère la réponse octet par octet ; le funnel du store fait un fetch full-buffer. Aucun `downloadTask` vers fichier, aucune reprise (`Range`/resumeData) nulle part.

Remplacer le corps de la Task de `networkData` (`:361-369`) par : `let (tmpURL, response) = try await urlSession.download(from: url)` (API async, écrit sur fichier, zéro buffer mémoire), vérifier le status HTTP, puis `await adopt(localFile: tmpURL, for: urlString)` (méthode existante, atomique), puis retourner `try Data(contentsOf: cachedFileURL, options: .mappedIfSafe)` — la lecture mappée (mmap) préserve le contrat `Task<Data,Error>` des awaiters sans pic mémoire.

### media-04 — Annuler un prefetch n'annule jamais les transferts ; TaskGroups sans plafond · **P2** · effort M
**Constat.** Le funnel exécute chaque fetch dans une `Task<Data,Error>` non structurée : annuler l'awaiter (un prefetch) n'annule jamais le transfert réseau sous-jacent. Les TaskGroups de prefetch ajoutent une task par média sans aucun plafond de concurrence.
**Preuve.** `DiskCacheStore.swift:361-376` : Task non structurée, awaiters en `try await task.value` sans `withTaskCancellationHandler`. `ConversationMediaHandler.swift:26` (`inFlightTask?.cancel()`) et `FeedViewModel.swift:1198` (`prefetchTask?.cancel()`) n'arrêtent que l'enfilage de nouvelles sous-tâches (guards `!Task.isCancelled` aux `:47`/`:1210`). **Impact.** Scroll rapide dans le feed ou burst d'événements socket : les fenêtres de prefetch successives lancent des transferts inarrêtables qui s'accumulent (bande passante, batterie) et concurrencent les cellules visibles sans aucune priorité.

1. `packages/MeeshySDK/Sources/MeeshySDK/Cache/DiskCacheStore.swift` : enrichir `InFlightDownload` d'un `var awaiterCount: Int` et d'un flag `let externallyOwned: Bool` (true quand créé par `registerInFlightDownload` `:394-407` — jamais annulé par le refcount, car c'est le transfert d'une surface visible).

Dans `networkData` (`:355-377`) et côté callers internes qui attendent un in-flight : incrémenter `awaiterCount` avant l'await, envelopper `try await task.value` dans `withTaskCancellationHandler` dont le `onCancel` décrémente (hop d'acteur) et fait `task.cancel()` quand le compte tombe à 0 ET `!externallyOwned`.
3. Plafonner les TaskGroups de prefetch à 4 slots : dans `ConversationMediaHandler.prefetchRecentMedia` (`:44-79`) et `FeedViewModel.prefetchMedia` (`:1207-1245`), collecter d'abord les clés à préfetcher puis itérer en fenêtre glissante (4 `addTask` initiaux, puis un `addTask` par `group.next()`).

**Risque de régression.** Ne jamais annuler un transfert tenu par une surface visible : le flag `externallyOwned` exempte les tasks enregistrées par un owner explicite, verrouillé par le test dédié « 2 awaiters, 1 annule → transfert continue ; tous annulent → annulé ».

## Questions ouvertes

1. **Auth des endpoints média.** Les endpoints `GET /api/v1/attachments/file/**` exigent-ils une authentification ? Aucun fetch média client n'envoie d'`Authorization` — si le gateway les protège un jour, tout le pipeline 401 silencieusement (les catch retournent placeholder/`hasFailed` sans distinction). Le volet TLS est traité par net-03 ; le volet auth reste un chantier transverse gateway.
2. **Reprise d'un upload de STORY après kill.** `StoryPublishQueue` existe (et est purgée au logout) mais son write-ahead n'a pas été audité ici — vérifier la parité avec l'outbox messages (le correctif media-01 ne couvre que les conversations).
3. **Divergence `publicUrl` (gateway tus-handler) vs `serverOrigin` (app) en staging.** Elle rendrait incohérentes la clé de seed auteur (media-09) et potentiellement les clés de lecture entre surfaces — c'est le déclencheur commun des écarts latents media-02/media-09.
4. **`DownloadBadgeView` pour les attachments `.file` (documents).** `start()` early-return et `checkCache` retourne toujours false pour `.file` — si le badge est monté pour un document, c'est un badge permanent non fonctionnel.
5. **Après rejeu outbox d'un média requeued**, la bulle garde les ids d'attachments locaux jamais réconciliés (commentaire `ConversationViewModel.swift:2864-2870`) — l'affichage ne tient que par le seed cache `file://` ; confirmer qu'aucune surface (galerie, forward) ne dépend des ids serveur.
