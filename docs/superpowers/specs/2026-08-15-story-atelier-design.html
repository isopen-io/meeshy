01 · État des lieux

Deux mondes, zéro contrat

02 · Diagnostic

Pourquoi 85 vues ?

Trois causes racines, toutes structurelles — aucune n'est un accident d'implémentation.

Chaque capacité a engendré ses propres écrans

Un outil = une toolbar + une topbar + des bulles flottantes + un panneau d'options. Le quatuor texte est le miroir exact du quatuor dessin. La timeline a reproduit le motif à l'échelle : container, tracks, overlays, inspecteurs — 32 vues pour un seul outil.

MeeshyUI/Story/Timeline/Views · StoryTextEdit* · StoryDrawing*

Le serveur accepte tout, donc rien ne converge

StoryEffectsSchema est en passthrough() : dessins, keyframes, transitions et clés inconnues passent sans validation. La doc du schéma Prisma décrit un format obsolète. Résultat : le web écrit des clés que iOS ne lit pas, et inversement.

services/gateway/src/routes/posts/types.ts:159-176 · schema.prisma:3040-3055

Deux contrats de publication, sept portes d'entrée

Création : file offline, retour toujours true. Édition : en ligne uniquement, composer laissé ouvert hors-ligne. Sept sites distincts posent showStoryComposer = true, deux façades montent le même composer avec des callbacks différents.

03 · Principes

Les outils sont des données, pas des vues

Tout est un StoryElement

Média, texte, sticker, audio, lieu, trait de dessin : un seul type { kind, transform, timing, payload }. Un registre de renderers (un par kind) remplace les 6 layers du canvas et les branches par type.

Le lecteur EST l'aperçu

Composer et lecteur partagent le même registre de rendu. L'aperçu devient le lecteur en mode preview — WYSIWYG garanti par construction, zéro vue dédiée.

Panneaux générés, pas dessinés

Un ToolDescriptor { icône, contrôles[] } décrit chaque outil ; le Dock génère son panneau depuis des contrôles typés (slider, couleur, segmenté, liste). Ajouter « filtres » = ajouter un descripteur — un outil ne peut plus être « déclaré mais inatteignable ».

Piloté par l'usage réel

L'immense majorité des stories est photo/vidéo + texte + audio. Ce chemin tient sur le canvas seul, sans modal. La timeline, les keyframes et les transitions restent disponibles — repliées dans le Dock comme inspecteur avancé, plus comme monde parallèle.

Une porte, un contrat

Un seul point de montage racine, une seule intention d'ouverture (create | edit | draft). Publication et édition passent par la même file offline — le contrat asymétrique disparaît.

Le format est une propriété

Story, post, réel : le même atelier, la même barre de publication, la même file. type ne change que la destination (tray ou feed), le TTL (20 h ou permanent) et l'endroit où vit le texte — jamais l'outil.

Le schéma est le produit

storyEffects v2 : schéma Zod strict dans packages/shared, types Swift générés depuis la même source. Le serveur refuse l'inconnu ; les plateformes ne peuvent plus diverger en silence.

04 · Architecture cible

Cinq vues, identiques sur web et iOS

Chaque vue a une responsabilité unique. Tout ce qui varie — types d'éléments, outils, contrôles — est de la donnée interprétée par ces cinq surfaces. Et parce que le format n'est qu'une propriété, ces cinq surfaces publient aussi bien une story qu'un post ou un réel.

Deux conséquences structurantes. D'abord, la « vue sticker » n'existe plus comme vue : c'est un contrôle grid du Dock, alimenté par un provider — comme la carte du lieu ou la bibliothèque de sons. 05 · Un seul atelier

Story, post, réel : le même geste de publication

La base de données l'affirme déjà — PostType {POST, REEL, STORY, STATUS} sur un seul modèle Post, blob de canvas compris. Seuls les clients maintiennent quatre composeurs parallèles : StoryComposer, PostComposer (même bug d'upload), AudioPostComposer, et la tentative morte UnifiedPostComposer. L'atelier achève ce que le serveur a commencé.

L'Atelier — les 5 mêmes vuesun canvas, un dock, une barre de publication, une file offline
TYPE : STORYTray · visible 20 h puis archivée · les textes sont des éléments du canvas, traduits objet par objet · même surface sociale que REEL — seule la fenêtre diffère
TYPE : POSTFeed · permanent · le texte principal EST Post.content (indexé, pipeline translatePost) · le canvas s'anime dans la carte, exactement comme une story
TYPE : REELFeed vidéo · plein écran · le même canvas en vidéo-first, overlays en éléments · qualification serveur inchangée (REEL → POST si non qualifiant)

Deux règles suffisent à tenir l'unification — et ce sont des règles produit, pas des règles techniques :

Le texte du post EST le content

En mode Post, le bloc de texte principal saisi dans l'atelier ne devient pas un élément de canvas : il voyage en Post.content — sélectionnable, indexé, traduit par le pipeline translatePost existant, affiché en texte natif dans le feed avec l'indicateur discret du Prisme. Les textes posés sur le canvas restent des éléments de composition.

Le canvas voyage avec le post

Photos, vidéos, textes décoratifs, sons, stickers, dessins partent dans le même blob v2, quel que soit le format. Le feed les rend via le CanvasPlayer — le registre du Reader embarqué dans la carte : lecture automatique en sourdine, boucle, tap pour passer en plein écran immersif. Composer un post riche, c'est composer une story qui ne s'efface pas.

Les sept cas complexes — deux options chacun

C1 · Mentions & hashtags

Option A — champ content seulementAutocomplétion dans le champ texte des modes Post/Réel, en réutilisant le contrôleur des commentaires/messages. Sur le canvas, @ reste du texte décoratif ; l'extraction serveur (resolvePostMentions, extractHashtags) fait foi.
Option B — élément « mention » de canvasUn vrai élément à payload { userId } : tap dans le Reader ouvre le profil, y compris en story. Nécessite une extension du contrat (kind sticker, payload mention) et un rendu interactif.

Recommandation : A en phase 5 (zéro contrat nouveau), B ensuite comme extension du kind sticker — les deux sont compatibles, B n'invalide rien de A.

C2 · L'audio express (vocal rapide)

Option A — tout par le canvasL'audio est toujours un élément audio-first du canvas (cover auto façon ReelAudioBackdrop). Un seul chemin — mais deux taps de plus pour le vocal du quotidien.
Option B — raccourci d'AmorceBouton micro dans l'Amorce : enregistrer → publier direct. L'atelier fabrique le canvas minimal en coulisse et émet le même PublishIntent — aucun chemin de publication séparé.

Recommandation : B par-dessus A. Le raccourci produit le même objet que le chemin long — les trois chemins de publication audio iOS divergents meurent, la friction du vocal rapide reste nulle.

C3 · Slides story ↔ carrousel post

Option A — 1 slide = 1 carteEn mode Post, le SlideStrip devient le carrousel : l'ordre des slides EST l'ordre des cartes, PostMedia.order est enfin écrit à la publication, le feed pagine le CanvasPlayer avec des points.
Option B — pas de slides en PostUn seul canvas + grille de médias ordonnée manuellement dans le Dock ; le carrousel du feed est une liste de médias nus, sans composition par carte.

Recommandation : A — un seul modèle mental (le même SlideStrip partout), et le comportement de B reste atteignable en n'utilisant qu'une slide. Corrige au passage le tri de lecture qui ment.

C4 · Repost & quote

Option A — repost = PublishIntentrepostOfId passe par la Barre de publication : audience, langue et texte de quote au même endroit que tout le reste. La route /repost côté client disparaît — le serveur résout déjà repostOfId au create (PostService.ts:173-190).
Option B — route dédiée conservéeGarder /repost et enfin envoyer RepostSchema.visibility (le champ existe, aucun chemin feed ne le remplit). Correctif minimal, unification différée.

Recommandation : A — c'est l'esprit « un seul verbe ». B est le correctif d'attente acceptable si la phase 5 est découpée.

C5 · Le lieu (pastille vs métadonnée)

Option A — deux lieux indépendantsLa pastille de canvas (élément) et la métadonnée de publication (metadata.location) se posent séparément. Flexible, mais deux vérités possibles pour un même post.
Option B — une source, deux rendusUn seul lieu choisi dans le panneau : métadonnée toujours, pastille optionnelle « Afficher sur le canvas ». La découvrabilité (geoPoint, premier client de discoverabilityPrecision) est un toggle du même panneau.

Recommandation : B — une seule source de vérité, et la fuite iOS (lieu perdu sur les chemins inline) devient structurellement impossible.

C6 · La langue (publication vs objet)

Option A — par objet seulementComme la story aujourd'hui : chaque texte déclare sa langue, le content prend detectLanguage. Simple, mais le web continue de publier sans langue fiable.
Option B — héritage + surchargeLangue de publication dans la Barre (préremplie par détection, envoyée comme originalLanguage — corrige le web) ; chaque objet texte hérite, surcharge possible via l'onglet Langue (S3c).

Recommandation : B — le Prisme reçoit enfin une langue fiable sur tous les formats, et le cas multilingue par objet reste entier.

C7 · L'édition d'un post publié

Option A — l'atelier completL'intent edit rouvre l'atelier : tout est éditable (médias ±, lieu tri-état, type, langue), UpdatePost.mediaIds devient enfin vivant, le reset d'engagement (contentEditedAt) s'applique.
Option B — édition légère + escaladeUn inline rapide (texte, visibilité) dans le feed, et « Ouvrir dans l'atelier » pour le reste. Deux surfaces, mais le correctif rapide reste à un tap.

Recommandation : A comme socle (une porte), B comme raccourci de menu contextuel — même endpoint, pas de logique dupliquée.

07 · L'acquis préservé

La rupture porte sur les vues, jamais sur les fondations

Rompre avec les 85 vues et le passthrough(), oui — mais tout ce que le système fait déjà bien reste en place, tel quel, sous l'atelier. Ce ne sont pas des concessions au legacy : ce sont les acquis qui rendent la refonte possible.

✓
Traduction pilotée par l'audience

triggerStoryTextTranslation cible les langues des destinataires réels (pas 5 langues fixes), fusionne dans les objets texte, diffuse story:translation-updated. Le Prisme Linguistique intact.

✓
Pipeline audio 3 étages

Whisper → NLLB → TTS, transcription mobile prioritaire, repli serveur. L'enregistreur du Dock s'y branche sans le toucher.

✓
File offline + brouillons iOS

StoryPublishQueue (778 l.) et StoryDraftStore (1 024 l.) deviennent les moteurs de l'Étagère — inchangés, enfin exposés partout, y compris pour l'édition.

✓
Visibilité 6 niveaux + broadcast filtré

PUBLIC → ONLY, picker EXCEPT/ONLY, et le correctif de fuite du fan-out (broadcastStoryCreated) restent la référence.

✓
Éphémère sans destruction

Masquée après 20 h, jamais supprimée : archive auteur, republication (POST /republish), repost. L'atelier ne fait que donner enfin un client web à ces routes.

✓
Édition = « redevenue non-vue »

contentEditedAt → reset d'engagement diffusé via story:updated. Le comportement produit le plus fin du domaine, conservé à l'identique.

✓
Uploads TUS + propriété des médias

/uploads + claimableMediaWhere : le bon pipeline existe déjà — la refonte le généralise au web au lieu de le remplacer.

✓
Le moteur de gestes du canvas iOS

La manipulation directe (drag, pinch, rotation, guides, édition inline) est la partie réussie des 48 900 lignes. Elle devient le socle du Canvas — repliée derrière son API, pas réécrite.

✓
Idempotence & sons de bibliothèque

clientMutationId + withMutationLog contre les doubles publications ; capture et attribution des sons empruntés (captureSounds) inchangées.

L'audit du lecteur iOS (en-tête, crédit sonore, durées, progression, rail d'actions, traduction) tranche surface par surface : à gauche les conventions déjà justes — elles passent dans l'atelier telles quelles ; à droite les endroits où iOS se contredit lui-même — c'est là, et seulement là, que la rupture réduit la friction.

Ruptures assumées — là où iOS se contredit

Six frictions à résoudre

Le réel refabrique son crédit sonore à la main (borrowedSoundLabel, pill statique) → l'atome partagé partout, décompte compris : « Aïcha · ♫ Nuits d'été · 0:15 »
Le crédit d'en-tête ignore les sons foreground (fond uniquement) → le résolveur considère toutes les pistes : plus d'attribution manquée
Deux échelles temporelles (« 2h » au reader et au feed, « il y a 3 jours » dans Mes stories) → la compacte partout
Retour à l'original atteignable seulement via le picker → geste direct « maintenir le texte », aligné sur la bulle de conversation
Badge langue à l'opposé du contenu traduit (rail bas-droite vs texte haut-gauche) → le signal rejoint l'en-tête
Rail à 8 entrées au bord du scroll sur les petits écrans → la feuille d'engagement (S12) absorbe commentaires et réactions détaillées

Une story = un réel temporaire

C'est déjà vrai en base — une story EST un Post — mais les clients ne l'honorent pas. Le design l'érige en règle : une story publiée porte toute la surface sociale d'un réel, servie par les mêmes endpoints et le même Prisme. L'unique écart est la fenêtre de visibilité.

09 · Le contrat partagé

canvas v2 — une source, tous formats

Le schéma vit dans packages/shared, seul endroit autorisé à le définir. Le gateway le valide en mode strict, le web l'importe, le Swift est généré depuis lui. Story, post ou réel : le canvas est le même objet (stocké dans la colonne Post.storyEffects existante).

// packages/shared/schemas/canvas.ts — source de vérité unique
const StoryElement = z.object({
  id:        z.string(),
  kind:      z.enum(['media', 'text', 'sticker', 'audio', 'location', 'drawing']),
  transform: Transform,          // x, y, scale, rotation, z
  timing:    Timing.optional(),  // startTime, duration, fadeIn, fadeOut
  payload:   z.discriminatedUnion('kind', [MediaPayload, TextPayload, …]),
})

const CanvasV2 = z.object({
  v:          z.literal(2),
  background: Background,        // clé canonique — l'alias backgroundColor meurt ici
  aspect:     z.enum(['9:16', '16:9']),
  elements:   z.array(StoryElement).max(80),
  transitions: Transitions.optional(),
}).strict()                      // fini le passthrough : l'inconnu est refusé
// La publication — un seul verbe, le format est un champ
const PublishIntent = z.object({
  type:     z.enum(['STORY', 'POST', 'REEL']),
  content:  z.string().max(5000).optional(), // POST/REEL : le texte natif → pipeline translatePost
  canvas:   CanvasV2.optional(),             // le même canvas animé, quel que soit le format
  audience: Audience,                        // STORY → FRIENDS par défaut, POST → PUBLIC
})
// STORY : content est composé depuis les textes du canvas (index de recherche)
// POST  : content EST le texte du post ; le canvas s'anime dans la carte du feed
// REEL  : canvas vidéo-first ; la qualification serveur décide, comme aujourd'hui

Corrections embarquées par le passage au contrat, côté web : upload via POST /uploads (TUS, uploadcontext: story) pour que PostService.createPost puisse réellement rattacher les PostMedia ; clé background canonique ; TTL optimiste aligné sur les 20 h serveur ; et enfin des clients pour GET /posts/stories/mine, PUT /posts/:id et POST /posts/:id/republish, aujourd'hui sans aucun consommateur web.

11 · Chemin de migration

Six phases, chacune livrable seule

1

Contrat

storyEffects v2 strict dans packages/shared (le serveur accepte v1 et v2 pendant la transition). Fix immédiats web : pipeline TUS, clé background, TTL 20 h. C'est la phase qui corrige les bugs de production.

2

Noyau

Registre StoryElement + Canvas unifié, branché d'abord côté lecture. Le lecteur devenant le moteur de rendu unique, l'aperçu WYSIWYG tombe gratuitement.

3

Dock

Migration outil par outil vers les ToolDescriptor : texte, dessin, audio, puis timeline repliée en inspecteur avancé. Chaque outil migré supprime son quatuor de vues.

4

Étagère & publication

Fusion tray / Mes stories / brouillons, porte d'entrée unique à intention typée, file offline pour l'édition comme pour la création — StoryPublishQueue et StoryDraftStore restent les moteurs, inchangés. Le web gagne brouillons, édition et archive en implémentant les 5 mêmes vues. La feuille d'engagement (commentaires, réactions, réponse) devient le composant commun aux trois formats.

5

Un seul atelier

Le sélecteur de format arrive dans la Barre de publication : PostComposer et AudioPostComposer migrent sur l'atelier, le texte principal voyage en Post.content (pipeline translatePost intact), le feed rend le canvas animé via le CanvasPlayer, les réels suivent en vidéo-first. C'est la phase qui tient la promesse « publier posts et stories de la même manière ».

6

Démolition

Suppression du code mort déjà identifié (UnifiedPostComposer et sa cascade, outil filters orphelin, StoryModels.swift dupliqué), retrait des composeurs legacy et du support v1, mise à jour de la doc Prisma.
