## 2026-11-09 : Une montée de libsignal est UN lot, sur les quatre plateformes, avec ses vecteurs régénérés (#17113)

**Statut** : Accepté (décision porteur du 2026-11-09, commentaire 6737719415 de #17113).

**Contexte** : un message scellé par libsignal sur une plateforme ne s'ouvre ailleurs que si les deux bouts parlent un format que l'autre lit. Le dépôt déclarait libsignal à quatre endroits, et ils avaient divergé : la passerelle en 0.106.1 puis 0.106.2 et shared en 0.106.2 (deux PR Dependabot, dont #17227, un correctif que la règle « ignorer mineures et majeures » laissait passer), iOS et Android en 0.105.4. Rien ne le voyait.

**Décisions** :
- **Une version, partout** : 0.106.2 depuis ce lot. Elle est déclarée par `services/gateway/package.json`, `packages/shared/package.json`, `packages/LibSignalClient/LIBSIGNAL_VERSION` (avec l'URL de la release `libsignal-ffi-v<version>` et sa somme de contrôle dans `Package.swift`), `apps/android/gradle/libs.versions.toml`, plus deux échos Android (`LibsignalNotices.VERSION`, `scripts/jvm-check/build.gradle.kts`) et le champ `libsignal` de `fixtures/libsignal/cross-platform.vectors.json`. La garde `__tests__/ci/libsignal-version-alignment.test.ts` exige qu'elles soient toutes identiques et exactes.
- **Une montée = un seul lot qui touche les quatre plateformes**, dans cet ordre :
  1. déplacer `fixtures/libsignal/cross-platform.vectors.json` dans `fixtures/libsignal/legacy/<ancienne version>.vectors.json` (jamais le supprimer) ;
  2. monter les déclarations ci-dessus ; côté iOS, recopier sans modification `swift/Sources/LibSignalClient`, `swift/Tests/LibSignalClientTests`, `LICENSE` et `acknowledgments/acknowledgments-ios.plist` du nouveau tag, laisser `libsignal-ffi.yml` publier la release, puis reporter sa somme de contrôle ; côté Android, recopier `acknowledgments-android.md` dans `feature/settings/src/main/res/raw/libsignal_acknowledgments.md` ; mettre `NOTICE` à jour ;
  3. régénérer les vecteurs (`cd packages/shared && node scripts/generate-libsignal-vectors.mjs`) ;
  4. prouver les trois bancs : jest (passerelle, `libsignal-cross-vectors.test.ts`), `sdk-tests.yml` (`LibsignalCrossPlatformVectorTests`), `android.yml` (`:core:e2ee`, `LibsignalCrossPlatformVectorsTest`).
- **Une session persistée avant une montée survit à la montée** (#9231) : chaque banc rejoue aussi chaque jeu de `legacy/`, sessions sérialisées comprises, avec la version courante. Le jeu scellé en 0.105.4, la version des sessions déjà persistées sur les appareils, est exigé par la garde. Une version qui ne lit plus un jeu de `legacy/` ne se monte pas.
- **Aucune montée automatique** : `.github/dependabot.yml` exclut `@signalapp/libsignal-client` sans restriction de type (correctifs compris) dans les trois entrées npm qui le voient (racine, passerelle, shared). Une entrée Gradle, si elle est créée, devra exclure `org.signal:*` de même ; la garde le vérifie.

**Hors du périmètre** : les vecteurs ne sont scellés que par Node. Des vecteurs scellés par les bindings Swift et Java sont suivis par #17126.

### Ce que la 0.106 change dans la vie d'une session : Tahini (audit du 2026-11-09)

Entre v0.105.4 et v0.106.2, l'amont introduit **Tahini**, une politique de gestion des sessions par appareil que les notes de version ne mentionnent pas (`rust/protocol/src/tahini.rs`, nouveau). Le format du fil et des enregistrements reste lisible dans les deux sens (vecteurs croisés, `legacy/0.105.4.vectors.json`), mais le comportement change :

- **Nouveaux champs d'enregistrement** : `SessionStructure.origin` (qui a ouvert la session : locale, distante, ou `Legacy` pour une session d'avant Tahini) et `RecordStructure.tahini` (sens de la dernière action, compteur de changements de sens). Une session 0.105.4 relue en 0.106.2 porte `Legacy` : elle se comporte comme une session distante une fois acquittée, et comme une session locale non acquittée (`LocalNew`) tant qu'elle porte encore une pré-clé non acquittée.
- **Ouverture simultanée arbitrée** (`decide_initiation_placement`) : quand une session ouverte par le pair arrive alors qu'une session active existe, l'arbitrage par identifiant ne joue que si la session active n'est pas encore acquittée par le pair ET que les identités concordent ; alors la session dont l'identifiant est le plus grand prend la place active et l'autre part en archive. Dans tous les autres cas (session active déjà acquittée, identité différente), la session entrante prend la place active. Mesuré par `services/gateway/src/services/e2ee/__tests__/libsignal-tahini.test.ts` : les deux premiers messages s'ouvrent, puis l'échange reprend sans perte, en 0.105.4 comme en 0.106.2.
- **Détecteur d'interblocage** : après plus de 5 changements de sens entre un envoi et une réception sur une session archivée (`MAX_DIR_CHANGES`, `on_receive_inactive`), la session active est archivée pour forcer une nouvelle ouverture.
- **Une session archivée ne redevient plus jamais active** : en 0.105.4, déchiffrer sur une session archivée la remettait en place active (`promote_old_session`) ; en 0.106.2 cette fonction a disparu (« Tahini never promotes archived sessions to current », `session_management.rs`). Un message reçu sur une archive s'ouvre, mais la réponse part sur la session active.
- **Trois sessions archivées au lieu de quarante** (`consts.rs` : `ARCHIVED_STATES_MAX_LENGTH = 40` devient `MAX_ARCHIVED_SESSIONS = 3`). Mesuré par le même banc : un SignalMessage en vol s'ouvre encore après 3 redémarrages de session côté destinataire, et plus après 4 (refusé au déchiffrement) ; en 0.105.4, il s'ouvrait encore après 40 et plus après 41. Le banc simule ces redémarrages par des ouvertures LOCALES chez le destinataire (`processPreKeyBundle`), chacune archivant la session active ; des ouvertures distantes successives remplissent l'archive de la même façon.
- **`session_cipher_legacy` est retiré** : il n'était appelé par aucun code de Meeshy.

**Conséquences pour Meeshy** :
- **Pré-clés à usage unique** : après une rupture (interblocage cassé, ou ouverture simultanée perdue), un appareil n'a plus de session active vers son pair. Les scelleurs (`E2EEMessageSealer.withSessions`, `packages/MeeshySDK/Sources/MeeshyE2EE/E2EEMessageSealer.swift`, et `E2eeMessageSealer.withSessions`, `apps/android/core/e2ee/.../E2eeMessageSealer.kt`) relancent alors `startSession` depuis un bundle neuf, ce qui consomme une pré-clé à usage unique de l'annuaire. Ce lot ne mesure pas si le réapprovisionnement suit une rafale de ruptures : c'est l'objet de #17261.
- **Messages en vol, chez le destinataire** : un message chiffré sur une session plus ancienne que les trois dernières archivées devient illisible, quand plusieurs ouvertures se succèdent pendant qu'un message est en route (appareil hors ligne longtemps, réinstallations répétées du pair).
- **Messages en vol, chez l'expéditeur : déjà pire avant ce lot.** Avant de rouvrir une session, les scelleurs appellent `deleteSession`, qui efface tout l'enregistrement de l'appareil pair, archives comprises : AUCUNE session archivée ne survit, ce qui est plus destructeur que la limite de 3. Ce comportement est antérieur au lot et ne protège de rien ; une réponse du pair encore en route sur l'ancienne session devient illisible. Il est suivi par #17261.
- **Témoins** : la passerelle fixe ces comportements (`libsignal-tahini.test.ts`). Le même témoin sur les bancs clients (SDK iOS, `:core:e2ee`) est suivi par #17261.

### Un PreKeySignalMessage est malléable : jamais d'identifiant calculé sur ses octets

Le quartet bas du premier octet d'un PreKeySignalMessage n'est couvert par aucun MAC (libsignal ne lit que le quartet haut, la version), et un champ protobuf inconnu ajouté à la fin est ignoré. Une copie ainsi modifiée s'ouvre avec le MÊME clair ; le premier exemplaire déchiffré gagne, et le suivant est refusé comme doublon (`DuplicatedMessage`). Comportement amont, identique en 0.105.4. Le SignalMessage, lui, n'est pas malléable : son premier octet est couvert par le MAC et un octet ajouté rend le protobuf invalide.

**Règle** : AUCUN identifiant, aucune déduplication, aucune signature ne se calcule sur les octets d'un PreKeySignalMessage (ni sur une enveloppe qui le contient tel quel) : deux octets différents peuvent porter le même message, et un relais (passerelle, pont DMA) qui dédupliquerait sur une empreinte de ces octets laisserait passer deux exemplaires dont un seul s'ouvre. Un identifiant de message se pose À CÔTÉ de la charge chiffrée, par l'émetteur. Témoin : `services/gateway/src/services/e2ee/__tests__/libsignal-prekey-malleability.test.ts` (copie 0x44 → 0x45, puis copie suivie de `f8 07 01` : les deux s'ouvrent, l'original est ensuite refusé comme doublon).

### Le web est la cinquième plateforme (#17114)

Le pont WASM du web (`packages/libsignal-wasm`, la crate officielle `libsignal-protocol` compilée vers wasm32) suit la même règle. Ses déclarations entrent dans la garde : `version` et `tag` de `packages/libsignal-wasm/Cargo.toml`, `apps/web/src/lib/e2ee/libsignal/manifest.json`, `WEB_LIBSIGNAL_ENGINE` (`apps/web/src/lib/licences/libsignal-engine.ts`) et `fixtures/libsignal/sealed-by/web.vectors.json`. Une montée ajoute donc deux étapes au lot :
- reconstruire le pont (`bash packages/libsignal-wasm/build.sh`, qui réécrit le binaire, sa colle et le condensat consigné) ;
- régénérer les vecteurs scellés par le web (`cd apps/web && bun scripts/generate-libsignal-web-vectors.ts`), que la passerelle et le banc web rejouent.

Aucune entrée Dependabot `cargo` n'existe : le pont ne monte jamais seul. Si une telle entrée est créée, elle devra ignorer `libsignal-protocol`.
