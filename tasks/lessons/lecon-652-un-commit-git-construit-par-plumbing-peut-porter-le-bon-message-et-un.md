## Leçon 652 — un commit git construit par plumbing peut porter le bon message et un arbre INCHANGÉ : vérifier le diff, jamais le SHA

2026-09-24, #7797/#7802 (`scripts/check-swift-catalog-dead-entries.mjs`). Pour corriger `BASELINE_DEAD_ENTRIES` sans toucher à l'arbre de travail (une session précédente avait déjà payé un `git checkout origin/dev -- .` accidentel sur une autre branche ce jour-là), j'ai construit le commit par plumbing : `git ls-tree <parent^{tree}> | sed 's/<ancien blob>/<nouveau blob>/' | git mktree`, puis `git commit-tree` et `git push origin <sha>:refs/heads/<branche>`.

**Le `sed` n'a jamais matché.** Le format exact de `git ls-tree` (mode, type, SHA, tabulation, chemin) ne correspondait pas au motif écrit à la volée ; `sed` a donc laissé chaque ligne INCHANGÉE, `git mktree` a fabriqué un arbre identique au parent, et `git commit-tree` a accepté sans broncher — un arbre égal au parent est un commit valide, juste VIDE. Le push a réussi, le SHA a changé, le sujet du commit annonçait « run test » et le correctif : tout avait l'air fait. La CI de la #7802 a mesuré 263 entrées mortes, pas 262 — la porteur a dû le redécouvrir et le corriger lui-même, dans le même lot que deux autres rouges (`fix(ios): ... le commit de la branche qui l'annonçait était vide`).

> **Un commit git construit hors du working tree (`commit-tree`, `mktree`, manipulation du index) doit être vérifié par un `git diff <parent> <nouveau>` ou `git show --stat <nouveau>` avant d'être poussé — jamais seulement par le SHA retourné ou le message qu'on lui a donné.** Le SHA change toujours ; le message dit toujours ce qu'on voulait faire ; seul le diff dit ce qui a été fait. La même prudence vaut pour tout script qui réécrit une ligne trouvée par un motif texte plutôt que par une structure adressable : vérifier que le motif a MATCHÉ, pas seulement que la commande a réussi.
