## La passerelle dit « compte supprimé » au seul porteur d'un jeton signé de ce compte, et le nomme ; tout autre refus d'authentification reste générique (2026-10-21, #10264)

**Statut** : Accepté. Livré dans `dev` (historique écrasé depuis : les SHA cités sur l'issue ne se retrouvent plus, le code si). Recette staging avec un compte réellement purgé encore à faire avant promotion.

**Contexte** : un appareil garde pour un compte des données qui n'ont pas d'autre exemplaire (le carnet de progression du jeu et ses photos, #10237, D-200). Quand le compte est SUPPRIMÉ, elles doivent partir ; mais jusqu'ici la purge effaçait les sessions et désactivait la ligne, et la requête suivante de l'appareil rendait `401 { code: 'AUTH_FAILED', error: 'Invalid JWT token' }` — octet pour octet la réponse d'un jeton expiré, d'une session révoquée (« déconnecter les autres appareils », mot de passe changé) ou d'un jeton hérité hors fenêtre. Purger sur tout 401 effaçait des photos uniques à chaque expiration de jeton ; ne rien purger laissait les selfies d'un compte supprimé sur l'appareil.

**Décision** :
1. **Un code dédié, sur les statuts et les événements qui existent déjà.** `401 { code: 'ACCOUNT_DELETED', accountId }` sur toute route authentifiée (`createUnifiedAuthMiddleware`) et sur `POST /auth/refresh` ; `error { code: 'ACCOUNT_DELETED', accountId }` sur l'événement d'erreur du socket ; `auth:session-revoked` porte `deletedAccountId` à la PURGE seulement ; la réponse de `POST /account/deletion/resolve` action `purge` porte `data.deletedAccountId`. Rien ne change de statut ni d'événement : un ancien client lit un 401 comme avant. `accountId` est déclaré dans `errorResponseSchema` (`packages/shared/types/api-schemas/error.ts`) et émis par `sendError` / `sendAccountDeleted`.
2. **« Supprimé » a UNE preuve : une `AccountDeletionRequest` au statut `COMPLETED` sur une ligne qui n'est pas redevenue active** (`accountIsDeleted`, `services/auth/account-deleted.ts`). Les colonnes `isActive: false` + `deletedAt` ne prouvent rien : la suppression de modération (`UserManagementService.deleteUser`) les écrit aussi et `restoreUser` l'annule ; la fin de grâce (`GRACE_PERIOD_EXPIRED`) les écrit alors que l'annulation rend encore le compte. Ces trois cas gardent le refus générique (`AUTH_FAILED`, `SESSION_REVOKED`, « Account disabled » sans code). Une lecture qui lève vaut « pas supprimé » : un faux « supprimé » coûte des données irréversibles, un faux « générique » ne coûte qu'un retard de purge.
3. **Le code ne se dit qu'au porteur d'un jeton dont la SIGNATURE a été vérifiée pour ce compte, et le NOMME.** La ligne n'est lue qu'après `jwt.verify`, sur le seul chemin d'échec, déjà rare ; un jeton forgé au nom d'un identifiant ou une signature invalide n'apprennent pas que le compte a existé (l'oracle d'existence reste fermé). Un jeton EXPIRÉ d'un compte supprimé rend `AUTH_FAILED` : l'expiration ne dit rien du compte. La réponse porte `accountId`, l'identifiant du jeton signé, pour qu'un appareil qui a basculé de compte pendant le vol purge le bon.
4. **Le client ne purge que sur ce signal, et que le compte qu'il nomme, s'il est celui du jeton présenté.** Web : `deletedAccountOf` / `deletedAccountOfRevocation` / `ownDeletedAccount` (`apps/web/src/lib/api/account-deleted.ts`), `onAccountDeleted` du transport HTTP et du socket, geste `retireDeletedAccount` (session close si c'est le compte tenu, puis `accountVault.forget` qui emporte `meeshy-game-notebook-<id>`), retrait raté noté et rejoué au démarrage. iOS : `AccountDeletedSignal` (SDK) et `DeletedAccountRetirement` (app, #10482).

**Alternatives rejetées** :
- *Un statut 410* : distinguerait mieux sur le fil, mais un ancien client traitait 410 comme une erreur quelconque et gardait sa session ouverte ; le 401 la ferme partout, et le code suffit au nouveau client.
- *Lire `isActive: false` + `deletedAt`* : trois chemins réversibles écrivent ces colonnes (§ 2) ; chacun aurait purgé des photos d'un compte qui revient.
- *Lire la ligne avant la vérification de signature* : ouvrait un oracle « ce compte a existé » à quiconque forge un jeton au nom d'un identifiant.
- *Purger sur `auth:session-revoked` raison `logout_all_devices`* : la purge coupe les sessions sous cette raison générique, comme « déconnecter les autres appareils » ; sans `deletedAccountId`, rien ne les distingue.

**Témoins** : `src/__tests__/unit/middleware/auth-account-deleted.test.ts` (vraie route par `inject`, à travers le sérialiseur : supprimé ⇒ `ACCOUNT_DELETED` nommé ; désactivé, expiré, forgé ⇒ `AUTH_FAILED`, ligne jamais lue), `src/__tests__/unit/routes/auth/refresh-account-deleted.test.ts` (purge, grâce expirée, jeton hérité, session encore valide, signature invalide), `src/socketio/handlers/__tests__/AuthHandler.account-deleted.test.ts` ; web `apps/web/src/lib/api/account-deleted*.test.ts` (purge sur le seul code et pour le compte nommé, jamais sur `AUTH_FAILED` / `SESSION_REVOKED` / 401 sans code, jamais sous une identité d'invité ni pour un autre compte).

**Conséquences** : la suppression d'un compte efface aussi ce qu'il a laissé sur ses appareils, à la première requête de chacun. Ce que le lot ne fait pas : aucun message « ce compte a été supprimé » à l'écran de connexion (le web déconnecte sans l'expliquer, suivi de #10237) ; le refus générique reste la réponse d'un compte en grâce, et l'appareil garde ses photos jusqu'à la purge, par construction.
