## Une adresse prise montre son détenteur masqué ; « ce n'est pas moi » + code la transfère (2026-09-27, #8214)

Décisions porteur du 2026-09-27 : quand l'adresse existe, vérifiée ou non, on MONTRE l'identité du compte qui la détient, masquée comme pour un numéro déjà pris, et on demande « Est-ce vous ? ». « C'est moi » mène à la récupération par lien magique (clients, #8216). « Ce n'est pas moi » crée le compte, qui gagne l'adresse en saisissant le code — OBLIGATOIREMENT, même avec un numéro ; l'ancien compte perd l'adresse et garde pseudo, numéro et contenu.

Site unique : `services/auth/email-claim.ts`.

1. **`POST /auth/register` sur une adresse détenue** : reste `409 EMAIL_TAKEN` (l'app iOS publiée le comprend) et porte `emailOwner: { maskedDisplayName, maskedUsername, avatar? }` — `maskDisplayName` / `maskUsername`, les fonctions de `phoneOwnerInfo`. Jamais l'adresse ni l'identifiant du compte. Déclaré au schéma 409 (`emailOwnerSchema`, `packages/shared/types/api-schemas/auth.ts`, type `RegisterEmailOwner`) : fast-json-stringify retire en silence ce qui ne l'est pas. `RegistrationRefusal` le porte comme `suggestions` pour `USERNAME_TAKEN`. Le 409 reste PAYANT au limiteur, comme avant.
2. **`claimEmail: true`** : le compte naît **`isActive: false`**, sous une adresse d'attente à lui (`claim-<aléa>@claiming.meeshy.invalid`), l'adresse revendiquée dans la colonne neuve `User.claimedEmail`. Code + lien partent à l'adresse (l'e-mail de vérification habituel, qui nomme le pseudo du compte revendiquant) ; réponse `200 { status: 'verification-required', accountCreated: true, email, pendingSessionToken }` (forme #8055) — `email` est l'adresse REVENDIQUÉE, et le jeton d'attente se lie au compte revendiquant (`pendingSessionTokenForAccount` ; une recherche par adresse rendrait le détenteur). Aucune session, aucune annonce d'arrivée, aucun salon avant la preuve. **Pourquoi `isActive: false`** : toutes les portes (mot de passe, pseudo, numéro, lien magique, SMS) ne cherchent que des comptes actifs — la garde est fail-closed par construction, aucune porte n'a à se souvenir de la revendication. Sans détenteur, `claimEmail` est ignoré : inscription ordinaire.
3. **Une seule paire vit par adresse** : une nouvelle revendication éteint les clés des précédentes et libère leur pseudo (`claim-<id>`, `retireEarlierClaims`). Les essais de code restent donc bornés comme pour tout compte (limiteurs par adresse et par IP de `POST /auth/verify-email`) au lieu d'être multipliés par le nombre de revendications. **Redemander le code, c'est revendiquer à nouveau** (même `POST /auth/register`, `claimEmail: true`) : `POST /auth/resend-verification` sert le DÉTENTEUR de l'adresse, jamais une revendication.
4. **La preuve** passe par les routes existantes (`POST /auth/verify-email`, code OU lien) : une clé que le détenteur ne reconnaît pas est présentée aux revendications de l'adresse. Celle qui répond déclenche UNE transaction : consommation de la clé conditionnée à la paire lue → le détenteur reçoit `released-<id>@released.meeshy.invalid` (unique par construction, non routable RFC 2606), perd `emailVerifiedAt`, sa paire code + lien, ses liens magiques et ses réinitialisations (révoqués : ils prouvaient une boîte qu'il n'a plus), et porte `emailReleasedAt` → le revendiquant reçoit l'adresse, `emailVerifiedAt`, `isActive: true` → `SecurityEvent` `EMAIL_RELEASED_BY_CLAIM` (sévérité HIGH) sur le détenteur, métadonnées `claimantUserId`, `proof`, `hadPhone`, `hadPassword`, `wasVerified`, `reachable`. La libération PRÉCÈDE l'attribution dans la transaction : l'index `User_email_key` ne voit jamais deux lignes. Après : attentes marquées « prouvées », entrée dans le salon global, session ouverte par la route comme toute preuve.
5. **La course** : toute transaction qui perd (clé déjà consommée, conflit d'écriture `P2034`, index `P2002`, adresse prouvée par son détenteur APRÈS le dépôt de la revendication) s'annule en entier et rend `INVALID_VERIFICATION` — une revendication non prouvée n'a aucun effet. La dernière règle départage deux revendications nées ensemble : la première preuve gagne, et la seconde ne peut pas reprendre l'adresse à la gagnante.
6. **L'ancien compte reste connectable** par pseudo ou numéro : l'activation #8055 (`!emailVerifiedAt && !phoneNumber`) ne lui réclame plus d'adresse (`emailReleasedAt` non nul), et aucun code n'est renvoyé à l'adresse non routable. Ses sessions ouvertes ne sont pas révoquées — c'est toujours son compte.
7. **Ancien compte sans numéro ni mot de passe** (sa seule porte était le lien magique vers l'adresse) : il devient INATTEIGNABLE. Décision : le transfert a lieu quand même — la boîte a été prouvée par la personne qui la lit maintenant, et un compte qui ne peut plus rien prouver n'a plus de titre sur elle. Le compte n'est ni supprimé ni purgé : contenu, pseudo et conversations restent, et le `SecurityEvent` le marque `reachable: false` pour qu'un administrateur puisse lui rattacher une nouvelle adresse (`PATCH /admin/users/:userId`). Le même sort vaut pour un compte jamais vérifié sans numéro ni mot de passe, qui n'avait déjà aucune porte depuis #8055.
8. **Suites non traitées ici** : une revendication jamais prouvée ni renouvelée laisse un compte inactif qui réserve son pseudo (aucun balayage) ; l'e-mail de revendication n'avertit pas encore qu'il retire l'adresse à un compte existant ; `claimEmail` combiné à un `phoneTransferToken` n'exécute pas le transfert de numéro (le compte naît avec le numéro, inactif). Miroir Kotlin natif non touché (gel du 2026-09-16).
