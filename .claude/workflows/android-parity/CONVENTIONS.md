# Conventions du programme de parité Android ↔ iOS

> Règles CONTRAIGNANTES pour tout lot de parité (directive #11570). Elles sont arrêtées par l'architecture du 2026-10-22 et complètent `apps/android/ARCHITECTURE.md`, `apps/android/decisions.md` (ADR-001 à 024) et les `CLAUDE.md`. En cas d'écart, le `CLAUDE.md` racine fait foi.

## Règles

1. PLACEMENT DES MODULES (vérifié dans l'arbre) : :core:model = Kotlin pur sous me.meeshy.sdk.model.<zone> (lois, DTO, réducteurs, présentateurs) et me.meeshy.sdk.lang (Prisme) ; :core:network = me.meeshy.sdk.net + me.meeshy.sdk.net.api.<X>Api (seul endroit des littéraux de chemin, ApiPathLiteralGuardTest) ; :core:database = me.meeshy.core.database (entity/, dao/, migration/) ; :sdk-core = me.meeshy.sdk.<zone> (dépôts, coordinateurs, socket, outbox, playback, sans Compose) ; :sdk-ui = me.meeshy.ui.component.<zone> et me.meeshy.ui.theme (explicitApi : tout symbole exporté est public) ; features = package me.meeshy.app.<feature>, namespace Gradle me.meeshy.feature.<feature> ; :app = me.meeshy.app et me.meeshy.app.navigation. Pas de package me.meeshy.feature.*. Deux modules seulement sont créés : :feature:game (game-module-scaffold) et :feature:communities (communautes-liste-et-fiche).
2. JAMAIS FEATURE -> FEATURE : ce que deux features partagent descend dans :sdk-ui, :sdk-core ou :core:model ; un contenu croisé (onglet Postes dans le profil, plateau de stories dans le fil, appel depuis un profil) passe par un slot @Composable ou un CompositionLocal fourni par :app (LocalProfileSheetOpener, ProfileSheetEnvironment) ou par une interface de :sdk-core liée par Hilt (CallLauncher). :core:navigation reste un contrat de routes, sans écran.
3. LA LOGIQUE D'ABORD DANS :core:model : toute règle, résolveur, réduction d'état ou présentateur pur s'écrit en TDD dans :core:model (aucun import android.* ni androidx.*), prouvé en local par ./apps/android/meeshy.sh jvm-check (deux minutes) avant l'écran ; l'écran n'est qu'une projection mince. Les vecteurs de packages/shared/fixtures se rejouent avec le helper SharedFixtures (core/model/src/test/kotlin/me/meeshy/sdk/testutil/SharedFixtures.kt, livré par prisme-descente-stricte-loi, recherche du fichier en remontant comme PrismPreviewVectorParityTest). En cas d'écart TS/Swift, le TypeScript fait foi ; la PR cite les trois miroirs (packages/shared, packages/MeeshySDK, apps/android/core/model) d'une loi à miroirs.
4. UDF : un @HiltViewModel par écran, un @Immutable data class XUiState exposé en StateFlow (stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initial)), un puits fun onEvent(event: XUiEvent), les effets ponctuels en Channel<XUiEffect>(Channel.BUFFERED).receiveAsFlow() ; l'écran collecte par collectAsStateWithLifecycle(). Les rangées reçoivent des instantanés primitifs ou immuables, jamais un StateFlow ; LazyColumn avec key stable et contentType. On n'ajoute AUCUN champ à un UiState déjà gros (ChatUiState, StoryViewerUiState, ConversationListUiState) : le lot apporte son contrôleur et son StateFlow (ChatController @IntoSet posé par chat-viewmodel-state-split). Dispatchers injectés par @IoDispatcher / @DefaultDispatcher / @MainDispatcher (me.meeshy.core.common) ; tout listener asynchrone de socket ou de flux est enveloppé de try/catch.
5. CACHE-FIRST SWR : toute lecture de dépôt passe par cacheFirstFlow (me.meeshy.sdk.cache) et rend CacheResult.Fresh / Stale / Syncing / Empty selon une CachePolicy (fenêtres alignées sur iOS par persist-cache-policy-loadstate). Room est la source unique ; une panne réseau n'écrase jamais le cache ; squelette seulement sur Empty, jamais de spinner sur un cache non vide ; hors ligne = état discret, jamais un écran d'erreur. Une liste secondaire se range dans le CacheEntriesStore générique (clé + charge JSON, persist-cache-entries-store) : pas de nouvelle table Room pour une liste JSON par clé.
6. OUTBOX ET OPTIMISME : toute mutation = instantané -> application locale -> OutboxEntity -> réconciliation ou retour arrière sur l'issue. Un nouveau type d'action = une valeur OutboxKind ajoutée en fin d'enum + UN fichier de sender lié par @IntoMap @OutboxKindKey (persist-outbox-registre-senders) ; on n'édite jamais OutboxFlushWorker. Le sender rend transitoire ou définitif (persist-outbox-flusher-classifie) ; chaque rejeu porte X-Client-Mutation-Id = OutboxIds.cmid() ; 410 = déjà appliqué ; une mutation ne part jamais sous un autre compte que son propriétaire. Les gros médias passent par la file sur fichier (persist-media-file-queue) et TUS par tronçons (tus-envoi-depuis-fichier-reprenable), jamais un ByteArray en Room.
7. PRISME = UNE FONCTION : ReaderPrism + PrismTranslationResolver dans me.meeshy.sdk.lang (créés par prisme-descente-stricte-loi, miroir de resolvePrismTranslation de packages/shared/utils/conversation-helpers.ts et de ReaderPrism.swift) : rangs systemLanguage -> regionalLanguage -> customDestinationLanguage -> deviceLocale, descente STRICTE sans repli fr, la langue d'origine concourt à son rang, null = afficher l'original, jamais translations.first(). LanguageResolver.preferredContentLanguages (repli fr) ne sert que les défauts de composition. Aucune surface ne réécrit la boucle. La piste audio est élue par la langue du texte servi ; une surface qui annonce une langue rend le texte de cette langue ; la bannière push est déjà résolue par la passerelle (le client ne retraduit pas). Un témoin de rang s'écrit sur un rang autre que le premier.
8. PRÉSENCE : dérivation unique UserPresence.state(nowEpochMillis) (core/model/src/main/kotlin/me/meeshy/sdk/model/Presence.kt, règle 60 s / 3 min / 5 min) ; couleur uniquement par meeshyPresenceDotColor(PresenceState?) (sdk-ui MeeshyAvatar.kt), qui rend null pour OFFLINE = aucun point sur un avatar (le gris ne sert qu'aux affichages libellés). Présence absente de la charge servie = aucun point ; le client ne fabrique ni ne prolonge une présence (visibilité décidée par la passerelle : amis acceptés, soi, ADMIN/BIGBOSS) ; typing:start force le vert (ConversationTypingRoster) ; le point « ici » ne vient que de viewing:* ; un seul magasin de présence (presence-gestionnaire-unique).
9. THÈME ET ACCENT : couleurs uniquement par MeeshyTheme, LocalMeeshyTokens et MeeshyPalette (sdk-ui/theme, indigo #6366F1 -> #4338CA, aucune couleur dynamique Material You) ; espacements, rayons et mouvement par MeeshySpacing, MeeshyRadius, MeeshyMotion ; typographie MeeshyTypography en sp. Tout composant de contexte conversationnel reçoit l'accent en PARAMÈTRE, calculé par ApiConversation.accentColorPalette() (me.meeshy.sdk.theme, DynamicColorGenerator : 0,30 langue / 0,30 type / 0,40 thème, ±30°) et converti par hexColor() ; avatar sans photo = DynamicColorGenerator.colorForName ; les couleurs sémantiques (succès, alerte, erreur, info) restent statiques. Aucun littéral hexadécimal dans le code d'une feature. Le verre passe par MeeshyGlassSurface (RenderEffect dès l'API 31, repli opaque en 26-30), sans bibliothèque tierce de flou.
10. COMPOSANTS PARTAGÉS UNIQUES dans :sdk-ui (ou :sdk-core pour les moteurs) : avatar = MeeshyAvatar étendu par avatar-unique-et-branchement-social (photo, anneau de story, humeur, présence, contour) ; toasts = FeedbackToastCenter + MeeshyFeedbackToast (toasts-de-retour-globaux) ; haptiques = MeeshyHaptics (accessibilite-annonces-haptique-et-sens-de-lecture) ; squelettes = MeeshySkeletonBox ; états vides et erreurs = etats-vides-et-echecs-de-contenu ; en-tête repliable = CollapsibleHeader ; rangées glissantes, barre de réactions, texte riche, kit plein écran (plein-ecran-kit-chrome), scène = SceneCanvas (canvas-scene-unique-en-lecture) ; moteurs audio et vidéo et PlaybackCoordinator dans me.meeshy.sdk.playback (un seul pool ExoPlayer, aucun type Media3 exposé). Avant de créer un composant, chercher dans :sdk-ui et :sdk-core ; un lot qui a besoin d'un composant possédé par un lot non encore fusionné utilise l'atome existant derrière une couture, il n'en crée jamais une seconde version.
11. CHAÎNES ET LANGUES : ne jamais écrire à la main un libellé qui existe côté iOS (apps/ios/Meeshy/Localizable.xcstrings, catalogue MeeshyUI) : ajouter sa clé au manifeste du module (fragment apps/android/i18n/manifest/<module>.d/<lotkey>.json, statut adopted) puis lancer ./apps/android/meeshy.sh i18n, qui génère res/values{,-fr,-es,-pt,-de,-it,-ar}/strings_generated.xml (nom Android = clé iOS, points et tirets remplacés par _, spécificateurs positionnels). Un libellé propre à Android va dans un fichier NEUF par lot, res/values*/strings_<lotkey>.xml, dans CHAQUE dossier de langue présent dans le module (la garde garde-localisation-android échoue sinon) ; on n'édite jamais un strings.xml existant, sauf pour en retirer une clé adoptée. Sept langues cibles : en (défaut), fr, es, pt (sert pt-BR), de, it, ar ; arabe : start/end, Icons.AutoMirrored, jamais left/right, le canevas de story ne se miroite pas. Aucun littéral visible dans le Kotlin. La langue d'interface Automatique suit systemLanguage puis l'appareil (corrige ARCHITECTURE.md §14).
12. TESTS : TDD rouge -> vert ; comportement par l'API publique ; fonctions-fabriques plutôt que lateinit ou @Before mutables ; noms en backticks décrivant le comportement (style existant). :core:model : JUnit4 + Truth + coroutines-test (jvm-check). :feature:* : Robolectric + Turbine + MockK. Un appel réseau se teste en capturant la requête au dernier maillon (modèle PublicProfileEndpointTest) ; un corps sensible s'ajoute à SensitiveBodyLoggingGuard ; un champ @EncodeDefault a son test de JSON doré (MeeshyApi.json a encodeDefaults=false) ; tout champ nouveau est nullable ou a un défaut (vieille passerelle, vieille ligne Room). Une migration Room se teste avec MigrationTestHelper sur le schéma JSON versionné. Un lot n'est vert qu'avec un run android.yml vert sur sa PR.
13. BUDGET DE TAILLE : plafond dur 1200 lignes par fichier (1000 = découpage sans discussion), fonction <= 80 lignes ; ajouter à un fichier hors budget est interdit, on extrait d'abord. Hors budget aujourd'hui : ChatScreen.kt 2953, ChatViewModel.kt 2248, StoryComposerScreen.kt 2022, StoryComposerViewModel.kt 1235, MeeshyApp.kt 1202, MessageBubble.kt 1202, FeedComposerSheet.kt 1127 (gelé jusqu'à composer-retrait-des-anciens-composers), StoryViewerScreen.kt 1113, ConversationListViewModel.kt 1046. Après leur lot de découpage, ces fichiers n'acceptent que des hunks de câblage de cinq lignes au plus.
14. VERSIONS ET API : Kotlin 2.0.21, Compose BOM 2024.10.01 (UI et Foundation 1.7.x, Material3 1.3.x), navigation-compose 2.8.3 (routes @Serializable), lifecycle 2.8.6, Media3 1.4.1, Coil 2.7.0, Room 2.6.1, Hilt 2.52, WorkManager 2.9.1, minSdk 26 / targetSdk 35. N'utiliser que des API présentes dans ces versions (PullToRefreshBox, SwipeToDismissBox, AnchoredDraggable expérimental, rememberGraphicsLayer et toImageBitmap, BasicTextField(TextFieldState) sont disponibles) ; interdits : API Material3 1.4 ou Expressive, Modifier.scrollable2D, API Compose 1.8+, Coil 3 (io.coil-kt.coil3), DefaultPreloadManager de Media3 1.5. Toute API au-dessus de minSdk est gardée par Build.VERSION avec un repli explicite (RenderEffect 31, AGSL 33, ScreenCaptureCallback 34, reconnaissance vocale sur appareil 31/33, POST_NOTIFICATIONS 33).
15. DÉPENDANCES : aucune bibliothèque sans besoin ; plateforme, AndroidX et Maven Central d'abord ; version exacte compatible Kotlin 2.0.21 ; toute entrée passe par gradle/libs.versions.toml selon le protocole des fichiers partagés ; une capacité qui dépend des Play Services (ML Kit, cartes Google) est injectée et ABSENTE (jamais grisée) quand elle manque.
16. HILT ET POINTS D'EXTENSION : aucun @Provides nouveau dans SdkModule.kt, NetworkModule.kt ou AppModule.kt ; chaque lot crée son propre fichier @Module @InstallIn(SingletonComponent::class) à côté de son code (modèle ShareLinkEntryModule.kt) ; une interface Retrofit neuve = Retrofit injecté (singleton posé par reseau-pipeline-reessai-erreurs) + son module. Un seul point d'extension par besoin, en multibinding (Set<@JvmSuppressWildcards T>) : AppInitializer, AppOverlay, AppLocalsProvider, NavGraphContributor, RealtimeBinding, PerAccountCache (socle-points-d-extension-de-l-app), AppLifecycleHook (persist-app-lifecycle-hooks), HttpClientContributor (reseau-pipeline-reessai-erreurs), PushObserver (socle-pipeline-push-et-cycle-de-vie), senders @OutboxKindKey. Ne jamais créer un doublon (RealtimeAttachable, AppStartupTask, AppForegroundHook, SessionResettable, GlobalOverlays sont remplacés par les points ci-dessus).
17. NAVIGATION : routes typées @Serializable ; chaque domaine contribue ses destinations par un fichier propre app/src/main/kotlin/me/meeshy/app/navigation/graph/<Domaine>NavGraph.kt (ou <Feature>Destinations.kt) lié en @IntoSet NavGraphContributor ; MeeshyApp.kt et Routes.kt ne sont plus édités après le socle. Liens meeshy:// et https://meeshy.me : une loi unique (loi-liens-profonds dans :core:model) et un routeur unique (racine-liens-profonds-android) ; un lien à jeton d'e-mail ne s'ouvre jamais dans l'app. Une destination d'un tier ultérieur absente retombe sur l'écran d'accueil (couture), jamais sur un écran mort.
18. ACCESSIBILITÉ : cible tactile >= 48 dp, contentDescription et stateDescription localisés, sémantique fusionnée par bulle ou rangée avec actions personnalisées (réagir, répondre, transférer), ordre TalkBack logique, aucun état porté par la seule couleur, tailles en sp, Réduire les animations respecté par LocalReduceMotion (reduire-les-animations-et-micro-animations) avec repli en fondu, RTL complet.
19. SÉCURITÉ ET PROTECTION : chiffrement fail-closed (jamais de clair dans une conversation E2EE, jamais de repli en clair) ; aucun jeton ni contenu journalisé ; une protection de contenu (vue unique, flou, éphémère, chiffré) se mesure sur TOUT ce que la charge transporte (texte, fichier, URL, vignette, transcription, nom) ; FLAG_SECURE uniquement par le registre de bouclier-capture-ecran-android ; Json strict pour la cryptographie et l'authentification. Les lots de cryptographie, d'authentification et de migration de données passent par l'agent auditeur-adversarial avant fusion.
20. RÉTROCOMPATIBILITÉ PRODUCTION : tout champ de requête nouveau est optionnel, tout événement socket émis par Android est ignorable par une passerelle ancienne, tout champ ou kind inconnu reçu est toléré (et réémis tel quel pour la scène) ; une ancienne route ne se retire qu'à zéro usage mesuré.
21. ISSUE ET PR : un lot = une issue (titre sémantique en français, corps Contexte / Preuve / Critère de fin / dimensions visées, critères des lots absorbés recopiés) dans le milestone de parité Android ; branche claude/android-<lotkey> poussée avec son squelette dans les quinze minutes ; PR vers dev avec Closes #n, la liste des fichiers touchés, les lois à miroirs touchées et l'état des deux autres miroirs, la preuve (sortie jvm-check, run android.yml). Ce qui reste non mûr devient une issue, jamais une ligne de fichier.

## Protocole des fichiers partagés

1) SÉMANTIQUE DE merge_or_drop (à appliquer avant toute planification) : toute arête depends_on qui vise une source fusionnée ou dédoublonnée est redirigée vers sa cible (en suivant la chaîne) ; la cible garde ses propres depends_on PLUS ceux listés après « Hérite : » dans la raison, rien d'autre (vérifié : le graphe obtenu est acyclique) ; les critères d'acceptation et les tests de la source sont recopiés dans l'issue de la cible ; les fichiers de la source deviennent ceux de la cible. drop-not-applicable : l'arête est supprimée et l'issue se ferme en not-planned avec la raison. Une dépendance ext: se résout par ext_dep_map ; une ext mappée sur [] est un prérequis EXTERNE non bloquant : le lot livre derrière une couture inerte et lie l'issue externe. Une ext qui vise un lot d'un tier plus tardif est souple de même (destination masquée tant qu'absente).
2) FICHIERS CHAUDS (arêtes implicites) : tout lot dont android_files_touched (y compris ceux des lots absorbés) contient un fichier de cette table dépend implicitement du DERNIER lot de sa chaîne ; les membres d'une chaîne s'ordonnent entre eux dans l'ordre donné. MeeshyApp.kt, MeeshyApplication.kt, MainActivity.kt, SessionTeardown.kt, RealtimeSessionCoordinator.kt -> socle-points-d-extension-de-l-app ; gradle/libs.versions.toml -> dependances-gradle-scene-medias ; MeeshyDatabase.kt, DatabaseModule.kt -> persist-room-migrations ; MeeshyApi.kt, NetworkModule.kt -> reseau-pipeline-reessai-erreurs ; OutboxFlushWorker.kt, OutboxModel.kt -> persist-outbox-registre-senders ; sdk-core/conversation/MessageRepository.kt -> persist-messages-repository-decoupage ; SocketManager.kt -> socket-connexion-jeton-identite-idempotente ; MessageSocketManager.kt -> socket-routage-evenements-ordre-arrivee ; core/model Message.kt -> prisme-descente-stricte-loi > message-fil-decodage-complet-et-tolerant ; Conversation.kt -> liste-conversations-fil-complet-et-contrat-apercu ; Story.kt -> story-model-split-un-type-par-fichier ; ChatScreen.kt -> chat-screen-composables-split > chat-screen-hosts-and-composer-split > composer-state-and-isolation > composer-glass-shell ; ChatComposer.kt -> chat-screen-hosts-and-composer-split > composer-state-and-isolation > composer-glass-shell ; ChatViewModel.kt -> chat-viewmodel-state-split ; MessageBubble.kt -> chat-bulle-decoupage-composants ; ConversationListViewModel.kt -> liste-decoupage-viewmodel ; ConversationListScreen.kt -> liste-decoupage-ecran-jetons-lentille ; StoryComposerScreen.kt, StoryComposerViewModel.kt -> composer-socle-decoupage-et-dependances ; StoryViewerScreen.kt, StoryViewerViewModel.kt -> story-viewer-decomposition-and-nav-graph ; FeedScreen.kt -> feed-screen-split ; FeedViewModel.kt -> feed-room-cache-and-realtime ; CallViewModel.kt, CallScreen.kt -> calls-foundation-app-seams ; SettingsScreen.kt -> settings-notification-screen > settings-hub-iso-layout ; ProfileScreen.kt -> profile-own-page-split ; app/push/MeeshyFcmService.kt -> socle-pipeline-push-et-cycle-de-vie ; sdk-ui MeeshyAvatar.kt -> atomes-d-avatar-loi-humeur-et-non-lus. Après son lot propriétaire, un fichier chaud ne reçoit que des hunks de câblage (cinq lignes au plus) ; FeedComposerSheet.kt est gelé (seul composer-retrait-des-anciens-composers le retire).
3) VERROU DE SCHÉMA ROOM (mutex global, toutes pistes) : après persist-room-migrations (baseline v16 exportée, fin de fallbackToDestructiveMigration), un seul lot qui change le schéma est en vol à la fois dans tout le programme (étiquette room-schema). Il prend la version suivante libre AU MOMENT de la fusion, ajoute core/database/src/main/kotlin/me/meeshy/core/database/migration/Migration_<de>_<vers>.kt, le JSON core/database/schemas/me.meeshy.core.database.MeeshyDatabase/<vers>.json et son test MigrationTestHelper, et ajoute son entité en fin de liste @Database ; si un autre lot de schéma a fusionné entre-temps, il se rebase et renumérote. Avant de créer une table, vérifier qu'un CacheStore (persist-cache-entries-store) ne suffit pas.
4) FICHIERS D'ENREGISTREMENT : (a) settings.gradle.kts et app/build.gradle.kts : seuls game-module-scaffold et communautes-liste-et-fiche y ajoutent une ligne include / implementation(project(...)). (b) Navigation : une destination = un fichier NavGraph ou Destinations neuf lié en @IntoSet NavGraphContributor ; MeeshyApp.kt et Routes.kt ne bougent plus après le socle. (c) Hilt : un module par lot (fichier neuf) ; SdkModule.kt, NetworkModule.kt, AppModule.kt gelés. (d) Chaînes : strings_<lotkey>.xml neuf par dossier de langue ; manifeste i18n en fragments apps/android/i18n/manifest/<module>.d/<lotkey>.json (le lot table-correspondance-chaines fait lire ces fragments au générateur) ; les strings_generated.xml ne se fusionnent JAMAIS à la main : en conflit, prendre une version puis relancer ./apps/android/meeshy.sh i18n (le --check de la CI le garantit). (e) gradle/libs.versions.toml : dependances-gradle-scene-medias déclare d'un coup l'union connue des besoins (media3-session, media3-transformer, media3-effect, media3-common, media3-datasource en 1.4.1, coil-gif 2.7.0, lottie-compose, exifinterface, androidx.window, compose material3-adaptive 1.0.x et material3-window-size-class, CameraX 1.4.x, room-testing 2.6.1, okhttp mockwebserver 4.12.0, glance-material3, lifecycle-service) et les dépendances de test de :sdk-ui ; ensuite un lot qui a besoin d'une bibliothèque nouvelle (SQLCipher, core-telecom, ML Kit, carte, review, sharetarget, mediarouter) l'ajoute dans un bloc commenté « # lot: <lotkey> » en FIN des sections [versions] et [libraries], au plus un lot en vol par piste sur ce fichier. Déclarer au catalogue n'ajoute rien à l'APK : le build.gradle.kts du module ne reçoit la dépendance que dans le lot qui l'utilise. (f) AndroidManifest.xml de :app : hunks additifs balisés <!-- lot: <lotkey> --> ; un composant d'un module bibliothèque se déclare dans le manifeste de CE module (feature/calls/src/main/AndroidManifest.xml, sdk-core), fusionné par AGP. (g) OutboxKind : valeur ajoutée en fin d'enum, décodage tolérant par nom. (h) Événements socket : une famille = un fichier neuf XxxSocketEvents.kt dans :core:model + un applicateur RealtimeCacheApplier en @IntoSet ; MessageSocketManager est gelé après socket-routage-evenements-ordre-arrivee, et les call:* nouveaux vivent dans CallSocialSignalManager (calls-social-socket-events). (i) .github/workflows/android.yml : seuls persist-room-migrations (contrôle de schéma), table-correspondance-chaines (i18n --check) et jetons-couleurs-generes-depuis-ios le modifient.
5) CONCURRENCE : au plus trois lots en vol par piste ; avant de lancer un lot, l'orchestrateur vérifie que ses fichiers (hors fichiers d'enregistrement ci-dessus) sont disjoints de ceux de TOUS les lots en vol, toutes pistes confondues ; en cas de recouvrement, celui qui n'a encore rien écrit attend (règle de la branche poussée). Une dépendance qui appartient à une autre piste se résout quand sa PR est fusionnée dans dev ; on ne recopie jamais son code en avance. Juste avant l'auto-fusion, la PR se rebase sur dev ; un conflit sur un fichier d'enregistrement se résout en gardant les deux hunks, un fichier généré se régénère, une version Room se renumérote, puis la CI repasse.

## Orchestration (complément de la session du 2026-10-22)

- **Une branche, une PR par lot** : `claude/android-<clé du lot>` part de `dev`, et sa PR vise `dev` avec `Closes #<issue>`. La PR fusionne (merge commit, titre par défaut « Merge pull request #n from isopen-io/claude/android-<clé> ») dès que la CI est verte, conformément à #9226 : l'auto-merge du dépôt est désactivé, la fusion est donc faite par l'orchestrateur.
- **Le registre des lots fusionnés est l'historique de `dev`** : `git log origin/dev --merges --format=%s | grep -o 'claude/android-[a-z0-9-]*'`. Un lot ne démarre que si toutes ses dépendances (`deps` dans `plan/<piste>.json`) y figurent.
- **Un lot se réserve en poussant sa branche** (règle de la branche poussée tôt, #5243). Une session qui trouve `claude/android-<clé>` déjà poussée laisse ce lot.
- **Gate** : `android.yml` (assembleDebug + testDebugUnitTest) vert sur la PR. En local, `./apps/android/meeshy.sh jvm-check` prouve `:core:model`.
